# 跨轮任务状态持久化（C 方案）设计文档

> 状态：已实现（2026-09-21）。关键决策见 §7，落地见 §5 改动清单。
> 关联：多智能体协作 A 方案（并行执行）已落地，本文是其延续。

---

## 1. 背景与问题

当前「动态规划（Planner）」是**无状态**的：

- `PlannerService.plan(message)` 每轮根据用户目标重新规划；
- `PlannerRoundHandler.executeSteps` 一次性把整份计划跑完；
- 中间态（各步骤的产出 `outputs[]`、完成标记 `done[]`）只存在于**方法内局部变量**，方法返回即丢弃。

这带来三个现实问题：

| # | 问题 | 现象 |
|---|---|---|
| 1 | **长任务断点丢失** | 计划含 5+ 步且某步较慢时，服务重启 / 进程崩溃 / 部署发布，已跑完的步骤结果全部作废，用户需重新描述目标、重跑 |
| 2 | **不可暂停/恢复** | 用户无法「先执行到第 2 步，看完中间结果再决定是否继续」 |
| 3 | **无法审计任务历史** | 一次多步任务跑完，除了 `agent_trace.plan_json`（只有计划、无逐步结果）外，没有任何「哪个步骤在何时产出什么」的可追溯记录 |

目标：把「任务 → 步骤 → 步骤产出」的状态机落库，支持**断点续跑、暂停/恢复、逐步审计**。

---

## 2. 设计目标与非目标

**目标（本次要做）**

1. 一轮规划任务 = 一条 `task` 记录 + N 条 `task_step` 记录，持久化到 MySQL。
2. 每步执行完即落库其状态与产出（增量提交），不再依赖内存变量。
3. 支持「显式续跑」：用户点「继续执行」按钮触发，跳过已完成步骤、只跑剩余步骤。
4. 保留现有「无状态」行为作为默认：单轮能跑完时，体验与现在完全一致。

**非目标（本次不做，避免范围蔓延）**

- 不做跨会话的任务队列 / 异步调度（任务仍在对话内同步/流式执行）。
- 不做「人工审批步骤」（human-in-the-loop）——那是另一个独立方向。
- 不做步骤级并发跨进程协调（并行仍由单机线程池完成，落库只做状态记录）。
- 不做任务的定时触发。

## 3. 数据模型

### 3.1 新增表 `task`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(64) | 任务 ID（UUID） |
| `conversation_id` | VARCHAR(64) | 所属会话，关联 `conversation.id` |
| `user_goal` | TEXT | 用户原始目标（触发规划的那句原话） |
| `status` | VARCHAR(16) | 任务状态：`RUNNING` / `DONE` / `FAILED` / `CANCELLED` |
| `total_steps` | INT | 步骤总数（快照，避免反复数） |
| `done_steps` | INT | 已完成步骤数（冗余，供列表快速展示进度） |
| `result` | LONGTEXT | 最终汇总结果（汇总步产出 / 最后一个成功步骤产出） |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 最后更新时间 |

索引：`INDEX idx_task_conv (conversation_id, status)`（按会话查未完成任务）、主键 `id`。

### 3.2 新增表 `task_step`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `task_id` | VARCHAR(64) | 所属任务，关联 `task.id` |
| `step_index` | INT | 步骤下标（0 基，对应规划里 `steps` 数组位置） |
| `agent_code` | VARCHAR(64) | 本步执行的智能体编码 |
| `instruction` | TEXT | 给该智能体的指令 |
| `depends_on` | VARCHAR(500) | 依赖的前序步骤下标（JSON 数组，如 `[0,1]`） |
| `status` | VARCHAR(16) | 步骤状态：`PENDING` / `RUNNING` / `DONE` / `SKIPPED` / `FAILED` |
| `retry_count` | INT | 重试次数（0=未重试；续跑时对 FAILED 步骤重试一次，累计失败 ≥ 2 即放弃，见 §4.5） |
| `output` | LONGTEXT | 本步产出文本（成功时写入；失败/空为 NULL） |
| `error` | VARCHAR(1000) | 失败原因（`FAILED` 时） |
| `citations_json` | TEXT | 本步 RAG 引用（与 `chat_message.citations_json` 同构） |
| `started_at` | DATETIME | 开始执行时间 |
| `finished_at` | DATETIME | 完成时间 |

索引：`INDEX idx_step_task (task_id, step_index)`。

### 3.3 状态机

**任务（task.status）**

```
创建 → RUNNING ──┬── 全部步骤完成 → DONE
                 ├── 某步失败且无兜底 → FAILED
                 └── 用户取消 → CANCELLED
```

**步骤（task_step.status）**

```
PENDING ──执行开始──→ RUNNING ──┬── 成功产出 → DONE
                                ├── 被跳过(agent不存在) → SKIPPED
                                └── 异常 → FAILED ──续跑重试──→ RUNNING（重试一次）
                                        │
                                        └── 累计失败 ≥ 2 次 → 终态失败（不再重试，依赖步回落原始目标）
```

- `RUNNING` 是过渡态；步骤执行失败但「依赖它的后续步仍可继续」（前驱空则回落原始目标）时，该步标 `FAILED`，任务不因此整体失败。
- `FAILED` 步骤在续跑时重试一次；重试仍失败（`retry_count` 累计 ≥ 2）则判定为确定性失败，续跑时跳过、按「前驱失败」处理。
- 任务整体 `FAILED` 只在「最终结果为空、且兜底通用助手也失败」时发生。

## 4. 数据流：断点续跑

### 4.1 首次触发（正常一轮跑完）

```
用户消息
  → PlannerRoundHandler.handle
      → PlannerService.plan(message)          // 规划出 steps[]
      → 创建 task(status=RUNNING) + N 条 task_step(PENDING)
      → executeSteps(...)                     // 现有并行执行逻辑
           每步完成 → UPDATE task_step(status/output/citations/finished_at)
                     UPDATE task(done_steps)
      → 汇总步产出 → UPDATE task(status=DONE, result=...)
      → 回复用户（与现在一致）
```

### 4.2 显式续跑（重启后）

续跑采用**显式按钮**，不复用正常对话入口，避免「续跑 vs 新话题」的语义判断。

```
用户点聊天页顶部「继续执行」按钮
  → POST /api/chat/task/resume  {conversationId}
  → 后端查该会话唯一的 RUNNING 任务：
      task = SELECT * FROM task
             WHERE conversation_id=? AND status='RUNNING'
             LIMIT 1
  → 读回 task_step 全部（按 step_index 排序）
  → 已完成(DONE/SKIPPED/FAILED)步骤的 output 回填到内存 outputs[]
  → 只执行 status=PENDING 的剩余步骤（复用 executeSteps，跳过已完成）
  → 完成后收尾：task.status=DONE、result、回复（写 chat_message）
```

关键点：

- **续跑不重新规划**：计划已在 task_step 持久化，重规划会产出不一致步骤集、状态错位。
- **单会话单 RUNNING**：续跑入口无需 task_id，按 conversationId 定位唯一 RUNNING 任务即可，语义无歧义。

### 4.3 开新任务自动结旧

单 RUNNING 不变量下，唯一要处理的边界是「用户已有未完成任务，又发起新规划」：

```
用户直接发新消息（普通对话或新规划目标）
  → 系统正常处理该消息，不自动续跑、不自动取消旧任务
  → 若本轮走 Planner 且产出新计划：
      先把旧 RUNNING 任务 UPDATE status='CANCELLED'
      再创建新 task + task_step 并执行
```

即：**普通闲聊不碰旧任务；只有「新规划任务落地」的那一刻才结旧**。这保证「任一时刻至多一个进行中的规划任务」，且无需用户手动清理僵尸任务。

### 4.4 幂等与并发防护

- 续跑用「读任务 → 跑剩余步骤」方式，天然幂等：已完成步骤 `status=DONE` 不会重跑。
- 步骤状态更新用 `UPDATE ... WHERE id=? AND status=PENDING` 这类带前置条件的写，防止并发重复执行同一批步骤。
- 续跑入口对「不存在 RUNNING 任务」直接返回空/提示，不产生副作用。

### 4.5 失败步骤处理（重试退避）

**策略：`FAILED` 步骤续跑时重试一次；累计失败 ≥ 2 次则放弃（跳过）。**

- 续跑时的待执行集合 = `PENDING` ∪ `FAILED`（`retry_count < 2` 的 FAILED）。
- `runStep` 捕获异常时写 `error` 并把 `retry_count + 1`。
- 续跑执行前，对 `retry_count >= 2` 的 FAILED 步骤：不再重试，视为「前驱失败」（依赖它的步骤回落原始目标继续）。
- `SKIPPED`（agent 不存在）步骤**不重试**——这是确定性失败，重试无意义。

**为什么不用「异常分类」（TRANSIENT/FATAL）**：可重试性不必预先分类，靠「重试一次还失败就放弃」的退避策略天然收敛——既覆盖网络抖动这类偶发失败（重试成功），又避免确定性失败（agent 已删、SQL 语法错）陷入反复白重试。

**全失败收尾**：续跑跑完剩余步骤后，若仍无任何步骤产出可用结果（`outputs` 全 null），任务标 `FAILED`，不再无限兜底；最终结果沿用现有「从后往前找第一个非 null output」逻辑。

## 6. 关键设计决策与取舍

| 决策 | 理由 | 代价/边界 |
|---|---|---|
| 续跑**不重新规划** | 计划已持久化，重规划会产生不一致的步骤集，状态错位 | 用户目标变了需「开新任务」（新规划自动结旧） |
| 续跑走**显式按钮** | 消除「续跑 vs 新话题」的语义判断，入口明确、可控 | 多一步点击；需前端加提示条 |
| **单会话单 RUNNING** | 续跑入口按 conversationId 定位唯一任务，无需 task_id；避免并发孤儿 | 不支持同会话多任务并行（本次场景不需要） |
| 开新规划**自动结旧** | 保证单 RUNNING 不变量始终成立，无需用户手动清理 | 旧任务被 CANCELLED 不可恢复（可接受） |
| 结果**DONE 时写 chat_message** | 与现有 `savePlannerExchange` 一致，用户能在历史看到结果、后续轮可承接 | RUNNING 中断不写（避免半成品当整轮落库） |
| 失败步骤**重试一次退避** | 不用异常分类，靠「重试一次还失败就放弃」天然收敛，覆盖偶发失败、避免确定性失败反复白重试 | 需 `retry_count` 字段；确定性失败会白重试一次（代价一次 LLM 调用，可接受） |
| 步骤输出落库用 `LONGTEXT` | 步骤产出可能是大段文本（数据分析结果、SQL、图表描述） | 磁盘占用，但单任务步骤数有限，可接受 |
| 状态写库走**同步**（每步完成即写） | 断点续跑的前提是「已完成步骤已持久化」，异步写可能丢最后一步 | 每步多一次 DB 写，但步骤粒度粗（秒级），影响可忽略 |
| 任务生命周期=会话内 | 不引入跨会话调度，任务跟随对话走 | 跨会话续跑需单独设计（本次不做） |

## 7. 关键决策（已定案）

1. **续跑触发方式**：显式按钮 `POST /api/chat/task/resume`（按 conversationId 定位唯一 RUNNING 任务）。不自动接续。
2. **未完成任务上限**：单会话至多 1 个 `RUNNING` 任务；开新规划任务时自动把旧 RUNNING 标 `CANCELLED`。
3. **任务结果写记忆**：任务 `DONE` 时把「用户目标 → 最终 result」写入 `chat_message`（复用现有 `savePlannerExchange`）；`RUNNING` 中断不写。
4. **失败步骤处理**：`FAILED` 步骤续跑时重试一次，累计失败 ≥ 2 次则跳过（视为前驱失败）；`SKIPPED`（agent 不存在）不重试。不建独立 UI，`progress` 播报「步骤 X 失败，已跳过」。

## 8. 后续可扩展（本次不做，预留）

- 人工确认点（human-in-the-loop）：`task_step` 增加 `WAITING_APPROVAL` 状态。
- 步骤级结构化传参：`output` 从纯文本升级为 JSON 字段，后驱按 key 引用。
- 任务级异步调度：脱离对话请求，`task` 交给后台队列执行。
- 规划反思/重规划：任务 `FAILED` 后触发 LLM 重新规划剩余步骤。
