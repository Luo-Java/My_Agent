# 项目长期记忆（My_Agent）

## 约定与偏好
- **解析 LLM 返回的 JSON 不用 Jackson `ObjectMapper`**：用户明确"不要使用 ObjectMapper 处理结果"。改用 **Hutool** 的 `cn.hutool.json.JSONUtil` / `JSONObject` 解析（已在 pom.xml 引入 `cn.hutool:hutool-all:5.8.38`）。跨轮参数抽取、路由结果等一律 Hutool，不引入 ObjectMapper 解析路径。
- 用户偏好直接执行、小步快跑迭代；每次改动后必须真实编译验证（本机 Maven 在 `D:\software\Java\maven`，本地仓库同路径 `repository`，离线 `-o` 可用，启动器用 `java -cp boot/plexus-classworlds-2.11.0.jar` 绕过损坏的 mvn 脚本，**launcher 行模板见 `.workbuddy/memory/run_mvn.sh`**）。
- **离线打包必须加 `-Dmaven.legacyLocalRepo=true`**（Maven 3.9 resolver 内部属性，2026-09-07 验证）：绕过 resolver strict 校验 `_remote.repositories` 来源记录，否则 plugin 的 transitive 依赖（如 slf4j-api/jsr305）即使本地 jar 完整也 fail on offline mode。run_mvn.sh 已固化此 flag。
- **打包后不要启动项目做运行验证**（用户明确要求，2026-09-02）：构建/打包只到 `mvn package` 为止，不做 `java -jar` 启动验证，也不自动占用/释放 8080；服务启动与运行验证完全由用户自己从 IDE 控制。确需验证接口可提示用户自行启动后用 curl。
- **任何表结构变更（加/删字段、加/删表、改类型约束）必须同步改 `sql/schema.sql`**（用户明确要求，2026-09-03）：schema.sql 是全新建库的权威定义（spring.sql.init 已注释、不会自动建表，靠它手工建库），alter.sql 只负责存量库兼容补列——两条 SQL 文件要保持同一列的最终状态一致；改 DDL 时两处一起改，禁止只写 alter.sql 不动 schema.sql。

## 已知缺陷 / 坑
- **Spring AI 2.0.0：`stream()` + `@Tool` 必崩 `NoSuchElementException`**（`OpenAiChatModel$ChunkMerger` 对工具调用 `Optional` 直接 `.get()`）。带工具的智能体（天气）流式输出要改用 `call()` 走完工具循环拿完整答案，再分块模拟流式（`Flux.fromIterable(...).delayElements(...)`）。`call()` 路径无此问题。

## 架构要点
- 多 Agent 平台（Spring Boot 4 + Spring AI 2.0 + MyBatis-Plus）。`ChatService` 为编排门面，参数补全/路由/记忆合并/提示词分别在 `ParamFillingService`/`AgentRouter`/`MemoryMergeService`/`PromptService`。
- Agent 声明参数：`paramSchema`（JSON 数组）驱动对话中的追问补全，追问上限 `ParamFillingService.MAX_CLARIFY=3`；跨轮参数靠 AI 自带记忆(DBChatMemory)累积，不改动 Conversation 结构。
- **RAG / 知识库（MySQL 自存向量 + Chroma 加速副本双写，2026-09-03 起）**：表 `kb`（agent_id 非空=智能体专属库，NULL=全局库「通用知识库」，单例由 `KbService.getOrCreateGlobal()` synchronized 保证，因 MySQL 唯一索引对 NULL 不生效）+ `kb_chunk`（embedding MEDIUMTEXT 存 JSON float[]，**MySQL 永远是源**）。Embedding 用 DashScope `text-embedding-v3`（配置 `spring.ai.openai.embedding.model`，key/base-url 与 chat 共享）。**Chroma 接入**：官方 `spring-ai-chroma-store` 2.0.0（模块本体非 starter），本机服务 `http://127.0.0.1:8000`（yaml `chroma.base-url`/`chroma.collection-name`，默认 collection `kb_chunks`）；封装 `ChromaVectorStoreService`（lazy + initFailed 降级，upsert/delete/search 全 try-catch 只 warn）；写入链路 MySQL 先落再同步 Chroma（同名替换/rechunk/删文件/删库/删块全覆盖），`search()` Chroma 优先（where kb_id + cosine TopK）→ 空/异常回退 MySQL 全量余弦；`POST /api/kb/chroma/sync`（body kbId 缺省=全部库）幂等回填副本。Chroma 侧 chunk id(String) 作文档 id，metadata 带 kb_id(int)/source；collection 建 cosine 空间（相似度=1-distance 与 MySQL MIN_SCORE 口径一致）；doAdd 内部用同 EmbeddingModel 再向量化（双算，确定性输出一致）。管理/写入在 `KbService`（文件分块/Chroma 双写/sync），检索在 `KbSearchService`（2026-09-03 拆出，见下条），管理 REST 在 `/api/kb`。容错契约：读失败（`ObjectProvider<EmbeddingModel>.getIfAvailable()` 降级）返回空串不阻塞对话，写失败抛 `AiBusinessException` 回滚。删 agent 时 `AgentService.deleteAgent` 用 mapper 级联删专属库（避免循环依赖）。DB DDL 追加在 `sql/schema.sql`，但 `spring.sql.init` 注释 → 建表需手动执行。
- **会话级 RAG 纯开关 + 自动多库（2026-09-03 起，语义经「显式选库」最终拍板「纯开关自动多库」）**：conversation 只存 `rag_enabled` TINYINT(1) NOT NULL DEFAULT 0（旧显式选库 `rag_kb_id` 已废弃清理：alter.sql 语句移除、存量库 DROP COLUMN、代码零引用）。开启后每轮走 `KbSearchService.buildKbContext(Boolean ragEnabled, Agent agent, String query)`（2026-09-03 从 KbService 拆出，检索收敛点）：`ragTargets(agent)` 解析目标库 = **通用全局库（kb.agent_id IS NULL，只查不建）＋ 路由/绑定 agent 存在专属库时其专属库**；多库**一次合并检索**（Chroma 单 collection 按 kb_id OR 等值拼接一次查完、query 只向量化一次、ChromaHit 带 kbId 回溯归属库；整体失败/无命中回退 MySQL 单条 IN + 余弦，embedOne 只调一次），命中按相似度降序统一截断 **TOP_K_RAG=3** 注入 system；开关关/空查询/无命中=空串。注入点：`ChatComposer.buildRequest`（会话绑定 agent）/`buildDefaultRequest`（agent=null 兜底）/`PlannerRoundHandler.executeSteps`（每步传**当步步骤 agent**）——本体库始终匹配当轮 LLM 实际处理对象。更新接口 PUT `/api/chat/conversation/{id}/rag`（body `{enabled}`，`ConversationService.updateRagEnabled` 单趟 UPDATE）；前端「📚 资料库」下拉改 **iOS 滑块开关**（复用 planner-toggle 结构 + 绿色 .rag-toggle），会话恢复用 ragEnabled 回显。
- **知识库以「文件」为管理单元（2026-09-02 起）**：表 `kb_file`（kb_id+file_name 唯一，file_name 与 kb_chunk.source 一致 ≤200 字符）。上传 `POST /api/kb/{id}/upload` → `KbService.registerFile` 解析分块向量化入库并登记文件；**同名重传=替换**（解析向量化全成功后才删旧写新，事务回滚保护）；`GET /{id}/files` 列表、`DELETE /{id}/files/{fid}` 级联删块并回减 doc_count；删库/删 agent 级联删 kb_file；单块删除同步文件 chunk_count。手动文本 addChunks 接口保留兼容但 UI 已移除。RAG 问答注入暂不迭代（用户明确「先做文件功能」）。
- **分片策略与重叠（`ChunkingService` + `ChunkStrategy`）**：4 策略（fixed 固定/paragraph 段落/recursive 递归字符默认/markdown 标题感知，`GET /api/kb/chunk-strategies` 动态下发）；**overlap 块间重叠默认 60（0 关闭，上限 200）**——fixed 与超长兜底用滑窗（窗口 600/步长 600-ov），语义策略整块+聚合预算统一 `limit=600-ov` 再缝合（块头拼上一块尾至多 ov 字，单块仍 ≤600，ov=0 等价旧行为）。kb_file 存 chunk_strategy/chunk_overlap/raw_text（原文）→ `POST /{id}/files/{fid}/rechunk` 可不重传直接换策略/重叠重切（策略与重叠都未变才 no-op）。验证辅助：临时 java 单文件跑 `java -cp target/classes Xxx.java` 直接验证分片逻辑，无需启动服务。
- **分片配置在「知识库设置」（kb 级默认，2026-09-02）**：kb 表加 chunk_strategy/chunk_overlap 两列（默认 recursive/60）。上传/手动添加文本未显式指定时继承该库设置（`registerFile`/`addChunks` 经 `kbStrategy`/`kbOverlap` 解析，重叠 clamp [0,200]）；upload/rechunk 显式参数仍可覆盖（curl 兼容）。前端：设置弹窗（⚙，创建/编辑共用）配默认策略+重叠；上传面板不再逐文件选择，展示库默认并提示去设置改；文件行 🔄 重新分片保留（文件级覆盖）。
- **治理轮 2026-09-03（接口控制 + KbService 拆分 + 澄清核实）**：① `app.api-key`（环境变量 `APP_API_KEY`，默认空=放行）配置后 `ApiKeyInterceptor` 校验 `/api/**` 需带 `X-Api-Key`（兼容 `Authorization: Bearer`），401 常量时间比较；静态页与 OPTIONS 预检不拦（`ApiSecurityConfig` 注册）。② `KbService`(836 行) 拆出检索到 **`KbSearchService`**（buildKbContext/ragTargets/多库合并检索/searchAll/trimHits + 检索侧向量化自含，注入 kbMapper/chunkMapper/chromaStore/embeddingProvider，全局库同款查询内嵌避免循环依赖），KbService 留库管理/文件分块/Chroma 双写/sync（只写不读检索）；`ChatComposer` 注入改 KbSearchService。③ 澄清状态核实结论：`ParamFillingService` 是**无状态 DB 重放**设计（每轮 getHistory 全量重放推导，天然跨请求/重启/多实例一致），摘要不物理删消息故无断裂风险；**双向契约注释已写入** ParamFillingService 与 MemoryMergeService 类 javadoc（若未来物理归档旧消息须同步重放逻辑），不要再加 Conversation 字段。
- **多模态图片理解（2026-09-07 起，#139 闭环）**：DTO `ChatAttachment(type,caption,filename)` + `ChatRequest.attachments` 字段；后端 **`VisionService`** 用 Hutool HttpUtil 直连 dashscope OpenAI 兼容 `/chat/completions`（复用 spring.ai.openai.api-key/base-url，**仅切 model=qwen-vl-plus**），单图独立调用，单张 max 10MB、超时 30s，失败回退占位 caption；`POST /api/chat/vision/describe`（multipart files[]）→ `{"captions":[...],"filenames":[...]}`。**关键设计**：① 原始二进制**不进数据库、不进 RAG**（避免索引膨胀），caption 仅当轮注入，刷新/重开会话后不再出现；② 主对话模型不变（仍 qwen3.7-plus），识别另起 qwen-vl-plus，避免 vision 兼容风险；③ **附件拼接在 `ChatController` 层**（`composeWithAttachments`）——ChatService / ChatComposer / RoundHandler 全链路零改动，附件概念只留在 Controller，边界清晰；④ `agent.vision.*` 配置（VisionProperties @ConfigurationProperties(prefix="agent.vision")）。前端：输入框左下加 🖼 图片按钮 + hidden file input；多选（≤5 张）→ 本地 `URL.createObjectURL` 缩略图 → 发送前串行识别拿 caption → 拼进 attachments 发 stream；用户消息气泡加 .msg-attachments 渲染。前端 MAX_ATTACHMENTS=5 / MAX_ATTACHMENT_SIZE=10MB 与后端对齐。
