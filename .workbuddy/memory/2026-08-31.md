## 跟进修复：天气追问「北京呢？」被多问一次「日期？」（09:41）
- 现象（用户截图复测昨天修的 case）：路由已经修好（AI 没掉到通用助手），但点「北京呢？」之后 AI 又来一次追问「🔎 还需补充信息：日期（今天/明天/最近7天）」，而不是直接答「北京今天天气」。
- 根因：`ParamFillingService.clarifyScopedHistory` 之前以「最后一次正式回答」为界硬切历史。第 1 轮「今天天气怎么样」里用户明确说过「今天」→ 抽取器拿到 `日期=今天`；第 3 轮「北京呢？」走到 `decideClarify` 时，scoped 被切到「深圳今天天气」之后（空列表），加上当前消息「北京呢？」也没有日期字眼，于是 `日期` 被错判为缺失，再次追问。
- 修复：把硬切改成「按条数截取最近 12 条」。最近一个完整任务（原始请求 + 至多 MAX_CLARIFY=3 轮追问 + 回答）天然落在 12 条以内，让跟进任务能继承上一任务里用户**明确说过**的隐式上下文（最典型「今天」→ `日期=今天`）。
- 安全性：「禁止臆测」规则 + `paramSchema` 约束保证不串味——不同智能体 schema 不同，同智能体也只采用户明确表达过的取值。跨任务（先天气再翻译）不会污染；同智能体跨子任务（如「查北京→查上海→北京呢？」）会继承「今天」这类已明确的取值，正是期望行为。
- 改动文件：`src/main/java/org/luo/service/ParamFillingService.java`（`clarifyScopedHistory` 方法体 + Javadoc）。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务**。建议复测：同一会话走「今天天气怎么样 → 深圳 → 北京呢？ → 后天呢 → 上海呢？」，确认「北京呢？」直接返回北京今天天气、「后天呢」直接返回深圳后天天气、「上海呢」直接返回上海后天天气。

## 优化：记忆合并改用专用线程池（10:56）
- 背景：maybeMergeMemoryAsync 原来用 `Schedulers.boundedElastic().schedule(...)`，与 stream() 的 `subscribeOn(boundedElastic)` 共用同一个 Reactor 弹性调度器——记忆合并的秒级 LLM 调用会跟 SSE 对话执行抢同一批线程；线程名不可配、参数不可控、生命周期不托管。
- 改动：
  - 新增 `config/ExecutorConfig.java`：`@Bean("memoryMergeExecutor")` ThreadPoolTaskExecutor（core=2, max=4, queue=1000, 前缀 memory-merge-, waitForTasksToCompleteOnShutdown=true, await 10s）——低优先级后台小池子。
  - `MemoryMergeService` 注入 `@Qualifier("memoryMergeExecutor") Executor`，`maybeMergeMemoryAsync` 改用 `execute(...)`。
  - **拒绝处理**：execute 抛 RejectedExecutionException 时先把该会话从 merging 移除再记日志（否则占位卡死后续轮次），本次跳过、下一轮对话结束会再检查。
- 收益：与对话主链路线程隔离、参数集中可调、线程名可排查、Spring 托管优雅关闭。

- 编译通过（MVN_EXIT=0）。**生效：重启服务 + `USE agent; source sql/seed.sql`**。
