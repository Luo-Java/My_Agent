## 链路追踪（/api/trace）加归属过滤：每人看自己的，ADMIN 看全站
- 需求：`TraceController` 要按用户隔离，但系统管理员要能看到所有数据。
- 起因（前一轮核查确认的越权面）：`TraceController.list(conversationId, limit)` 完全没有用户维度 —— 不传 `conversationId` 就是查全站，返回体里带 `user_message`（用户原话原文）；`get(traceId)` 不校验归属。当时 `/api/chat/**` 已按用户隔离，只剩这条可观测旁路没跟上，属于「以为已经隔离了、实际留了个洞」的状态。
- **核心取舍：给 `agent_trace` 加 `user_id` 列 vs 查询侧 JOIN**。选了后者。理由：加列就得把身份一路传进异步落库链路（`RoundTrace` → `ChatService` → `traceExecutor` 线程），而 `agent_trace` 的设计原则是「纯旁路、不参与任何对话逻辑、删掉整张表对话照常跑」—— 把身份耦合进去就破了这条原则。归属改由 `JOIN conversation` 在查询侧判定，`conversation` 已有 `idx_user` 支撑。
- 另一个顺带确认的事实：**`deleteConversation` 只删 `chat_message` + `conversation`，不删 `agent_trace`**，所以会有孤儿记录（`conversation_id` 指向已删会话）。JOIN 天然查不出它们 —— 普通用户不可见、ADMIN 仍可见，正好符合「追踪作为旁路留档」的定位，不需要额外清理。
- 改动清单：
  - `mapper/ai/AgentTraceMapper.xml`：新增 `selectOwned`（`JOIN conversation` + 可选 `conversationId`，`LIMIT #{limit}`）与 `selectOwnedByTraceId`；文件内注释写清「为什么不加列」与「孤儿记录为何查不到」。
  - `AgentTraceMapper.java`：对应两个方法（`@Param` 三个/两个）。
  - `TraceService`：`list(conversationId, limit, userId, allUsers)`、`get(traceId, userId, allUsers)`；**删掉无归属的旧重载**（不留「顺手一调就漏」的口子，与「规划配额配置不支持关闭」同一种思路）；类注释从「三条原则」扩成「四条」，第 ④ 条即归属边界。
  - `TraceController`：`AuthContext.require()` 取身份 + `SysRoleCode.ADMIN` 判管理员（**不写 `"ADMIN"` 字面量**，用既有常量）；非 ADMIN 传了 `conversationId` 时先调 `ConversationService.checkAccess` 前置抛 404；`GET /{traceId}` 从「200 + null」改为**不存在与非本人统一 404**（防 traceId 探测；前端未调用该接口，无破坏）。
  - 前端：`chat.html` 追踪弹窗工具栏加 ADMIN 专用的「本会话 / 全部会话」切换（复用 `.cost-seg` 样式，不新造一套）；`app.js` 加 `traceModal.isAdmin` / `allConversations` / `setTraceScope` / `traceScopeHint` / `traceScopeEmptyText`，导出同步；空态与提示文案按范围分措辞。
- 一个前端坑（已在代码注释里写明）：`traceModal.isAdmin` 必须在**打开弹窗时**从 `Auth` 取一次存进 `reactive` —— `Auth.getUser()` 读的是 localStorage，**不是响应式的**，模板里直接调函数读它，登录态后到也不会触发重渲染，切换入口永远不出现。

  2. **真实库 SQL 语义**（新增 `.workbuddy/tools/verify_trace_scope_sql.py`，只读、不启动应用）：`agent_trace` 15 条 → JOIN 后 13 条（**证实 2 条孤儿记录**）；`conversation_id` 为空 0 条；单条归属查询正常。**关键是反证**：库里只有 `user_id=1` 一个用户，所以「user_id=1 查到 13 条」说明不了过滤在生效（全表 JOIN 也是 13 条）—— 补了「陌生 user_id=999 查列表 = 0 条」「带真实 trace_id + user_id=999 = 0 条」，这才证明过滤真的在过滤。

## 预览服务：修掉一个让权限相关界面静默失效的 mock 缺陷
- 现象：给追踪弹窗加 ADMIN 入口后，预览态下管理员**看不到**范围切换，但 `errcap` 为空、页面一切正常。
- 排查路径（值得复用）：先怀疑角色 mock → `curl -H "Referer: ...?__role=user"` 证明服务端角色判定正确 → 转去看前端，读 `auth.js` 发现 `hasRole()` 读的是 `user.roleCodes`，而 mock 写的是 **`roles`**（字段名不对，`Array.isArray(undefined)` → 恒 false）。
- 第二层真因（字段名改对后仍不生效）：预览服务只往 localStorage 注了 **token**、没注 **user**。而 `Auth.requireLogin()` 拿到 200 后**只解锁页面、不写 USER_KEY** —— 它信任已有的本地会话（真机上 user 是登录框写进去的）。于是预览态下 `Auth.getUser()` 恒为 null，`hasRole()` 恒 false。
- 修法：`PREVIEW_USER` 字段名对齐 `SysUserVO`（`roleIds` / `roleCodes` / `roleNames`，另补 email / lastLoginAt / createdAt，因为「个人信息」弹框要用），并在 `build_login_head` 里 **token 与 user 一起注入**，让预览态与真实「已登录」状态一致。
- 顺带新增预览能力（以后验权限相关的显隐都能用）：`?__role=user` 切换普通账号。角色经 **Referer 的 query** 传给 `/api/auth/me`（页面 fetch 默认带完整 Referer），因为该请求本身不带页面的 query。
- 同类潜在隐患：**任何 mock 只要字段名与真实 VO 不一致，前端能力就会静默失效**（不报错、不抛异常，只是入口不见了）。改 mock 前先核对 VO 定义。

  而 SQL 只 SELECT 5 列。上一节写的「成功率由服务层折算」根本没机会执行 —— MyBatis 在**构造对象**这一步就失败了。
- 根因（读 mybatis-3.5.19 sources 定的，非猜测）：
  `DefaultResultSetHandler#createResultObject` → record 无默认构造 → `createByConstructorSignature` →
  本项目未设 `arg-name-based-constructor-auto-mapping`（`MybatisConfiguration` 只默认改 `mapUnderscoreToCamelCase`，`Configuration` 里该字段默认 false）
  ⇒ 走 `applyColumnOrderBasedConstructorAutomapping`，**按列序映射**，且 L787 显式 `parameterTypes.length > rsw.getClassNames().size()` 就抛
  `ExecutorException: The constructor takes '6' arguments, but there are only '5' columns in the result set`。
  **编译期无感、无兜底、只有真跑到这条查询才 500** —— 之前只做了编译 + 前端 mock 探针，两层都盖不到它。
- 修法（拆成 record 上的派生方法，SQL 不凑列）：
  - `Overview` 分量缩到 5 个（与 SQL 列一一对应），`successRate` 改为 `@JsonProperty("successRate") public double successRate()` 派生（rounds/errors 纯函数，空表恒 100%）。
  - `ObservabilityService` 删掉「先查一回再 new 一个」的重建逻辑，只留 null 兜底。
  - 实证 Jackson 3（Boot 4 用 `tools.jackson`）**会**把这种非分量方法序列化出来：写了临时探针 `OverviewJsonProbe`
    （record + `@JsonProperty` 方法 / `getXxx` 方法两种），产出 `{"rounds":200,...,"successRate":96.5}` —— 前端 `overview.successRate` 照旧可用。
- 顺带排掉同类隐患：扫了全部 `resultType="org.luo.*"` 的 select（26 条），其余 record 投影列数/顺序都一致（`AnswerAgg` 3/3、`UsageAgg` 4/4、其余桶 4~9 全对），edu 的 VO 与 `EvalBatchSummary` 是 bean（按 setter 映射，不受此约束）。
- 新增自检：`.workbuddy/tools/check_record_projection_columns.py` —— 扫 mapper XML 的 record 投影，比对「顶层 SELECT 列数」与「record 分量数」，
  `--self-test` 用人为构造的 6 参数 / 3 列坏用例自证会报不一致（避免「永远 OK 的假检查器」）。本次实跑：26 条 / 一致 8 / 不一致 0 / 跳过 18。
- 文档与记忆：`ARCHITECTURE.md` §十 mapper 规则新增「record 投影三条硬约束」（个数=列数、列序一致、派生指标不入 SELECT）；
  `MEMORY.md` 教务段新增同一条红线 + 更正可观测条里「成功率由服务层折算」的旧说法；`ObservabilityMapper.xml` 头部注释写明该约束。

## 可观测面板：空窗口 500（聚合 NULL 进 primitive long）

用户实测：默认近 30 天正常，**点「近 7 天」接口 500** ——
`Error instantiating class org.luo.ai.dto.ObservabilitySummary$Overview with invalid types (long,long,long,long,long) or values (0,null,0,0,0)`。

**根因**：`aggregateOverview` 里 `errors` 那列写的是 `SUM(CASE WHEN status='error' THEN 1 ELSE 0 END)`，**唯独它没包 COALESCE**
（同句其它列包过才没一起炸）。SQL 聚合在**零行**时 `SUM/AVG/MAX/MIN` 全返回 NULL（`COUNT(*)` 例外），
而 `Overview` 的分量是 primitive `long` ⇒ MyBatis 反射构造时抛 `IllegalArgumentException`。
**只在「窗口内一行都没有」时触发**，有数据的窗口永远测不出来 —— 编译、前端探针、人工看页面三层都盖不住。

**修法**：errors 一律改 `COUNT(CASE WHEN status = 'error' THEN 1 END)`（COUNT 恒非 NULL，不需要 COALESCE），
`ObservabilityMapper.xml` 五处全改（overview/daily/byMode/byRouteSource/byAgent），头部注释补「A 类列数 / B 类聚合非 NULL」两条硬约束。

**验证**（四层，逐层递进）：
- **真实接口复现**：登录拿 token 直打 `?days=7` → `{"code":500}`；`?days=30` → 正常（15 轮）。即用户报的原始现象。
- **真实库 SQL 实证**（新脚本 `verify_observability_empty_window_sql.py`）：近 7 天 0 行成立；旧写法该窗口返回 **NULL**（= 异常里那个 null）；
  新写法返回 0；整条 overview 5 列全非 NULL；30 天窗口新旧写法等价（2 vs 2，证修复没改正常值）。全 PASS。
- **静态自查**（新脚本 `check_mapper_null_aggregates.py`）：修好后**高风险 0**；并**反证**过 —— 把 errors 退回旧写法，脚本精确命中
  `ObservabilityMapper.xml / aggregateOverview / errors / SUM / long / 高风险`，还原后归零。
- **前端三用例**（`verify_observability.py` 新增 EMPTY7，真的去点「近 7 天」按钮）：cards=`[0,100%,0 ms,0,0,0]`、5 处「暂无数据」、
  err=0、表格 0 行、dirty=false；ADMIN / USER 两旧用例仍 PASS。（EMPTY7 第一次跑就是 FAIL —— mock 分支我漏改了，正好当天然反证。）

**同类排查结论**：全项目**只有 observability 这一处**是 primitive 接收聚合值。`AnswerAgg`/`UsageAgg` 是 `Long`、`ScoreStatsVO` 是
`BigDecimal`、`EvalBatchSummary` 是 bean —— 都不炸（成绩统计的 NULL 表示「这组没成绩」，包成 0 反而错）。
**判据是「接收方能不能接住 null」，不是「写法好不好看」。**

**顺带修**：管理员分支**没有任何地方渲染 `error`**（`.ob-error` 只写在非管理员分支）⇒ 加载失败时页面纹丝不动、看起来像按钮坏了。
`observability.html` 补 `v-if="error"` 节点；`FRONTEND.md` 记下「错误提示必须落到界面上」「没数据与没成功分开渲染」两条。

`serve_preview.py`（days=7 → 空窗口 mock）；新增两个脚本。`mvn package` BUILD SUCCESS，jar 内 5 处 `COUNT(CASE`、0 处裸 `SUM(CASE`。

## 坑：脚本间用 `dirname³` 反推项目根，分子目录会全断

`verify_pages.py` / `verify_observability.py` / `verify_trace_scope_sql.py` 等都是
`ROOT = dirname(dirname(dirname(abspath(__file__))))` 再硬拼 `.workbuddy/tools/serve_preview.py`。
⇒ `tools/` 一旦分子目录，`dirname³` 落到 `tools/` 而非项目根，**全部跨脚本调用断**。
所以「文件太多」只能靠**删除 + 索引**解决，不能靠分目录（那样得先改 N 个脚本的路径推算）。
