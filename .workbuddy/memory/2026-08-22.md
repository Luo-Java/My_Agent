# 2026-08-22

## 智能路由改为强制 JSON 返回
`AgentRouter.route` 由原先的文本约定 `ROUTE=<编码>`/`NONE` 改为**强制 JSON**：system prompt 要求模型只输出 `{"route":true,"agentCode":"编码"}` 或 `{"route":false}`，不允许多余文字/代码块。
解析仍用正则（不碰 ObjectMapper，遵守项目约定）：`ROUTE_BOOL` 提取 `route` 布尔，`AGENT_CODE` 提取 `agentCode`；只有 `route:true` 且含非空 `agentCode` 才算命中，否则回退普通对话。`ChatService.chat` 第 147 行的调用签名不变，`mvn -o compile` 通过。

## 路由 JSON 解析改用 Hutool
用户拍板：不用正则、也不要 ObjectMapper，改用 **Hutool** 的 `JSONUtil.parseObj(reply)` 解析路由 JSON。`pom.xml` 新增 `cn.hutool:hutool-all:5.8.38`（本地仓库已有）。`AgentRouter.parseRouteCode` 改为 `JSONObject obj = JSONUtil.parseObj(reply)` → `obj.getBool("route", false)` / `obj.getStr("agentCode")`；route 非 true 或 agentCode 为空都回退普通对话。移除 `Pattern`/`Matcher` 与正则常量。`mvn -o compile` 通过。此约定（避免 ObjectMapper、用 Hutool 解析 LLM JSON）已写入 MEMORY.md。

- `applyFields` 中 agentCode 自动生成的旧注释已更新（现在创建时空编码会被校验拒绝）。`mvn -o compile` + `node --check app.js` 通过。

## 统一 LLM 回复判空（消除重复调用 + 堵 NPE）
原 `String reply = response.getResult() != null ? response.getResult().getOutput().getText() : null;` 在 `AgentRouter`/`PromptService`/`MemoryMergeService`/`ParamFillingService` 共 4 处重复（且前 3 处只判 `getResult()`、漏判 `getOutput()`，存在 NPE 隐患）。统一改为逐级局部变量判空：
```java
var generation = response.getResult();
var assistantMessage = generation != null ? generation.getOutput() : null;
String reply = assistantMessage != null ? assistantMessage.getText() : null;
```
每步只判一次、零重复调用，且 `getOutput()` 为 null 时已安全返回。`ParamFillingService` 内变量名为 `r` 而非 `response`。`mvn -o compile` 通过。

## paramSchema 解析改用 Hutool（与路由统一）
`ParamFillingService.parseSchema` 原先用正则（`OBJ_PATTERN`/`FIELD_PATTERN` + `readField`/`readBool`/`readOptions` 三个辅助）解析 `agent.paramSchema` JSON 数组。用户要求统一为 JSON 处理，改为 `JSONUtil.parseArray(json)` → 遍历 `JSONObject` 用 `getStr/getBool/getJSONArray` 读取，options 经 `toList(String.class)` 转 `List<String>`。移除 `Pattern`/`Matcher` import 及常量与三个 read* 方法；类注释同步更新（LLM 抽取结果仍逐行正则，paramSchema 配置用 Hutool 规避 ObjectMapper）。`mvn -o compile` 通过。

## 天气智能体改用 @Tool 真实接口查询
需求：原来天气智能体直接靠大模型编天气，改为基于天气接口 + Spring AI `@Tool` 查询，支持固定日期与日期范围，且「先解析日期 → 查询 → 结果处理」三段式。
- 新增 `org.luo.tool.DateResolver`（`@Tool resolveDate`）：纯 Java 解析自然语言日期/范围（今天/明天/后天/昨天、下周X/本周X、X月X日、YYYY-MM-DD、范围 `到/至/~/-`、未来N天），返回 Hutool JSON `{type:single/range,...}`。中文数字解析自己实现（去掉 `NumberChineseFormatter`，5.8.38 无此 API），覆盖零~九十九。
- 新增 `org.luo.tool.WeatherTools`（`@Tool queryWeatherByDate`/`queryWeatherByRange`）：基于 Open-Meteo（免费、无需 key）——城市 geocoding（`geocoding-api.open-meteo.com`）+ 预报（`api.open-meteo.com/v1/forecast`，`start_date`/`end_date` 支持范围），WMO `weather_code` 映射中文，结果整理成逐日摘要。Hutool `HttpUtil.get(url, 8000)` + `JSONUtil` 解析（规避 ObjectMapper）。geocoding 结果带 `ConcurrentHashMap` 缓存。
- `ChatService.buildRequest` 按 `agent.getAgentCode().equals("weather")` 挂 `.tools(weatherTools, dateResolver)`。
- 新增 `org.luo.DataInitializer`（`@PostConstruct` 幂等）：库内无 `agentCode=weather` 时，创建带「先 resolveDate → 再查天气工具 → 整理结果」引导 prompt 的天气智能体。
- 编译坑：`ChatService` 需 `import org.luo.tool.*`；`Map.of` 仅支持 ≤10 键值对，CODE_MAP 28 条改用 `Map.ofEntries`；Hutool `NumberChineseFormatter` 在 5.8.38 不存在（自实现中文数字）。`mvn -o compile` 通过。运行时天气查询需外网访问 Open-Meteo。

## 天气 /stream 报 NoSuchElementException（Spring AI 2.0.0 流式+工具缺陷）
天气走 `/api/chat/stream` 抛 `java.util.NoSuchElementException: No value present`，栈里全是 `OpenAiChatModel$ChunkMerger.chunkToChatCompletion`（无业务代码行）。
**根因**：Spring AI 2.0.0 的 `stream()` 在合并「工具调用分片」时，对 `Optional`（tool call 的 `function.name()`）直接 `.get()` 触发已知缺陷；该合并逻辑**仅流式路径**调用，非流式 `call()` 不涉及。天气智能体挂了 `.tools()`，故一进流式就崩。两个 `@Tool` 方法自身都 try/catch 返回错误文本，所以若是工具内部错，栈会是 `org.luo.tool`（可据此区分）。
**修复**：`ChatService.stream()` 中，对带工具的智能体（`hasToolAgent`，与 buildRequest 挂载判断一致，目前仅 `AgentEnum.WEATHER`）改用 `spec.call().content()` 走完「模型→工具→再回答」循环拿完整答案，再按 4 字一块 `Flux.fromIterable(...).delayElements(15ms)` 模拟流式输出；并在 `.doOnError`/`catch` 中补详细日志（含会话 ID + 完整异常）便于定位。`chat()` 同步路径本就用 `call()`，无此问题。`mvn -o compile` 通过。

## 天气接口 ZipException: invalid stored block lengths（Hutool 5.8.38 gzip 解压缺陷）
天气 `geocode()`/`doQuery()` 抓 Open-Meteo（Cloudflare）偶发 `ZipException: invalid stored block lengths`。**根因不是 JSON 解析**（`JSONUtil.parseObj` 不抛 ZipException），而是 `HttpUtil.get` 在收 gzip 响应时 Hutool 5.8.38 解压炸。
**修复**：新增 `WeatherTools.httpGet(url)`，改用 `HttpRequest.get(url).header("Accept-Encoding","identity").timeout(TIMEOUT).execute().body()` 显式禁用压缩，两个接口统一走它（移除 `HttpUtil` 改用 `HttpRequest` import）。`mvn -o compile` 通过。注意 Hutool 5.8.38 的 `HttpRequest` 工厂是 `get/post`（不是 `createGet`，编译会报「找不到符号」）。

## 工具注册表（ToolRegistry）：新增工具不再改 ChatService
用户指出 `spec.tools(weatherTools, dateResolver)` 仍需手动注入所有工具。落地「接口自声明 + 注册表自动收集」：
- 新增 `org.luo.tool.AgentToolBundle` 接口：`name()` / `description()` / `tools()` 三个方法，工具包实现并注册 `@Component`。
- 新增 `org.luo.tool.WeatherToolBundle`：声明天气能力（tools = `[dateResolver, weatherTools]`，注意先日期后天气）。
- 新增 `org.luo.tool.ToolRegistry`：构造注入 `List<AgentToolBundle>` 自动收集成 `Map<name, tools>`，提供 `getAllTools()`（全量平铺）、`hasBundle(name)`、`getTools(name)`、`listNames()`。
- `ChatService`：删掉 `WeatherTools`/`DateResolver` 字段注入，改注入 `ToolRegistry`；`buildRequest` 用 `spec.tools(toolRegistry.getAllTools())`。
- 收益：新增工具能力 = 写一个 `AgentToolBundle` 实现类，`ChatService`/`ToolRegistry` 零改动。`mvn compile` → MVN_EXIT=0。

## 接入 ToolSearchToolCallingAdvisor（动态工具发现，AI 自主决定调工具）
需求：工具不绑死 Agent、不全量预挂，由 AI 在对话中按需发现并调用。落地 Spring AI 2.0 的渐进式工具暴露。
- **依赖**：pom 新增 `org.springframework.ai:spring-ai-starter-tool-search-advisor:2.0.0`（BOM 未管理该 artifact 必须显式 version；**不要用 2.0.1**，其传递依赖 spring-boot-starter 4.1.1 与项目 4.0.7 冲突）。类在 `spring-ai-tool-search-advisor-2.0.0.jar`，包 `org.springframework.ai.chat.client.advisor.toolsearch.ToolSearchToolCallingAdvisor`。
- **新增** `org.luo.config.ToolSearchAdvisorConfig`：`ToolSearchToolCallingAdvisor.builder().toolIndex(new RegexToolIndex()).maxResults(5).build()`。Builder 默认 `toolCallingManager`/`sessionIdKeyName=ChatMemory.CONVERSATION_ID`（与现有 `.param(CONVERSATION_ID, conversationId)` 正好匹配）；`systemMessageSuffix` 为空时自动加载内置模板。
- **ChatService**：构造注入 advisor 并 `defaultAdvisors(memoryAdvisor, toolSearchAdvisor)`；`buildRequest` 删掉 `AgentEnum.WEATHER` 判断，改为所有对话 `spec.tools(weatherTools, dateResolver)`（全局能力池，AI 自主决定调不调/调哪个）；删 `hasToolAgent`，`stream()` 统一走 `streamToolAnswer`（因为任何对话都可能触发工具调用，2.0.0 stream+工具缺陷仍在）。`applyAgentOptions` 的 `.options(customizer)` 与 `.tools()` 互不覆盖（tools 存独立列表）。
- **机制**（源码确认）：advisor 仅在请求 options 是 `ToolCallingChatOptions`（即挂了 tools）时激活；`doInitializeLoop` 按 sessionId 索引进 RegexToolIndex（工具集指纹未变不重索引），`doBeforeCall` 只向模型暴露内置 `toolSearchTool`，模型搜索出工具名后再注入真实工具执行。`DefaultChatClient.autoRegisterToolCallingAdvisor` 检测到链中已有 `ToolAdvisor`（ToolSearchToolCallingAdvisor 是 ToolCallingAdvisor 子类 implements ToolAdvisor）会自动跳过默认 ToolCallingAdvisor，无双重工具循环；`validateSingleToolCallingAdvisor` 保证唯一。
- 编译：联网 `mvn compile` → MVN_EXIT=0。运行时仍要求：外网访问 Open-Meteo；流式是 call()+分块模拟（2.0.0 缺陷规避）。
- 遗留：DataInitializer 之前未落地（查无文件），天气智能体若库里 agentCode 不是 weather 也不影响（已不按 code 判断）。

## ToolRegistry 去重：多 Bundle 共享同一工具时的重复问题
用户指出：若新建 `TicketToolBundle` 也注入 `DateResolver`，`getAllTools()` 会把同一个 `DateResolver` 实例加两次，导致 Spring AI 收到两个同名 `@Tool` 方法。
**修复**：`getAllTools()` 改用 `IdentityHashMap` 做 `Set`（按对象引用去重），同一 Spring Bean 实例只出现一次。`mvn -o compile` 通过。

## 删除 AgentToolBundle，ToolRegistry 直接扫描 @Tool Bean
用户指出 `AgentToolBundle` 中间层多余——工具类本身已是 Spring Bean，直接扫描即可。
- 删除 `AgentToolBundle` 接口、`WeatherToolBundle` 实现类。
- `ToolRegistry` 重写：构造注入 `List<Object>`（Spring 全部 Bean），反射检查 `getClass().getMethods()` 是否有 `@Tool` 注解，有则收集。天然去重（Set 按引用），无需 Bundle 包装。
- 新增工具 = 写 `@Component` + `@Tool` 方法，零配置自动注册。`ChatService` 无需改动（仍调 `toolRegistry.getAllTools()`）。`mvn -o compile` 通过。

## ToolRegistry 改用标记接口 ToolProvider（替代反射扫描）
用户指出反射扫描所有 Bean 不够 Spring 风格。`@Tool` 是方法级注解，`getBeansWithAnnotation` 无法按方法注解查 Bean。
**方案**：定义空标记接口 `ToolProvider`，工具类 `implements ToolProvider`，Spring 原生注入 `List<ToolProvider>`。
- 新增 `ToolProvider.java`（空接口）。
- `DateResolver` / `WeatherTools` 加 `implements ToolProvider`。
- `ToolRegistry` 简化为 `ToolRegistry(List<ToolProvider>)` → `toArray()`，删掉反射、IdentityHashMap、Collections 全部 import。
- `ChatService` 无需改动。`mvn -o compile` 通过。

## ToolRegistry 预解析 ToolCallback（避免每会话重复反射）
用户指出每次 `spec.tools(原始Bean)` Spring AI 内部都要反射解析 `@Tool`。改为 `ToolRegistry` 构造时用 `MethodToolCallbackProvider.builder().toolObjects(toolProviders.toArray()).build().getToolCallbacks()` 一次性预解析为 `ToolCallback[]`，`ChatService` 改调 `spec.tools(toolRegistry.getToolCallbacks())`。注意：`spec.toolCallbacks()` 在 2.0 已废弃，统一走 `tools(Object...)`（传 ToolCallback 数组会被直接识别，不再反射）。`mvn -o compile` 通过。

## ToolUsageLoggingAdvisor 工具使用监控
需求：监控每次对话用了哪些工具。新增 `org.luo.advisor.ToolUsageLoggingAdvisor`（实现 `BaseAdvisor`，注意 2.0 的钩子是 `before()`/`after()`，不是老 API 的 doBeforeCall）：
- order = MAX_VALUE-100 → 链最内层，位于 ToolCallingAdvisor 工具循环**内部**，每轮模型调用都经过。
- `before()` 记录两个信息：① 本轮暴露（options.getToolCallbacks 的名字，能看到渐进式：第1轮只有 toolSearchTool，后续注入已发现工具）；② 已执行（对话历史 ToolResponseMessage 里的真实工具名）。
- `ChatService` 构造注入并加入 defaultAdvisors(memory, toolSearch, toolUsageLogging)。`mvn -o compile` 通过。
- Spring AI 2.0 Advisor API 要点：`CallAdvisor` 只有 `adviseCall(request, chain)`；`BaseAdvisor` 提供 `before/after` 默认编排 `chain.nextCall()`。

## 修复「新建对话」按钮失效（前端）
现象：点击「＋ 新建对话」没反应。根因：`app.js` 的 `goChat()` 逻辑为 `if (!currentId.value) newConversation(); else if (conversations.value.length === 0) newConversation();`——一旦已有会话（currentId 有值、列表非空），点击只切视图不新建。
修复：`goChat()` 改为 `async` 且无条件 `await newConversation()`（总是创建新会话）。`node --check` 通过；`mvn compile` 后 `target/classes/static/js/app.js` 同步（Spring Boot 静态资源从 classpath 读，编译即生效，无需重启），curl 确认线上已返回新版本。
