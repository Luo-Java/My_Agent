# 2026-08-28 开发日志

## 新增：顺序工作流（Sequential Workflow）——多 Agent 链式执行
- 需求：让多个 Agent/步骤按顺序执行，前一步输出作为后一步输入。例：用户提问 → 天气 Agent 查询 → 翻译 Agent 把结果译成英文。
- 设计：**工作流本身就是一个 Agent 行**（agent 表新增 `workflow` TEXT 列存 JSON 步骤数组）。这样路由、参数补全、追问绑定、话题切换等既有机制零改动即可复用；只有"执行阶段"从单次调用换成链式。
- 数据格式（`agent.workflow`）：
  ```json
  [{"agentCode":"weather","instruction":"查询用户指定城市的天气，输出简洁中文描述"},
   {"agentCode":"translate","instruction":"把上面的结果翻译成英文，只输出译文"}]
  ```
- 改动文件：
  - `schema.sql` / `alter.sql`：agent 表加 `workflow` TEXT 列（alter.sql 负责旧库补列，已在 application.yaml 的 schema-locations 中）。
  - `Agent.java`：加 `workflow` 字段 + 注释。
  - `UpsertAgentRequest.java`：record 加 `workflow` 分量（插在 paramSchema 之后）。⚠️ 该 DTO 是位置构造，`AgentController.update` 第 73 行需同步补 `req.workflow()`，否则编译不过。
  - `AgentService.applyFields`：`if (req.workflow() != null) a.setWorkflow(req.workflow());`
  - `ChatService`：
    - 新增 `internalChatClient`（无记忆 Advisor）：`chatClientBuilder.clone().defaultAdvisors(toolUsageLoggingAdvisor).build()`。**clone 必须在 defaultAdvisors 之前调用**，否则会继承到记忆 Advisor。
    - 新增 `runWorkflowIfConfigured()`：agent.workflow 非空则走工作流，产出为空/解析失败自动退回普通单智能体回答。
    - 新增 `runWorkflow()`：先滤掉 agentCode 不存在的步骤（避免影响"最后一步"判定）→ 逐步执行；第 1 步输入=用户原始消息+长期记忆+已确认参数，后续步输入=`上一步的输出` + 本步 instruction；中间步骤用 internalChatClient（不落历史），最后一步用 chatClient（落库 [原始提问→最终结果]）；单步失败/返回空则跳过沿用上一步结果。
    - 新增 `parseWorkflow()`（Hutool JSONUtil 解析，与路由/参数解析一致，规避 ObjectMapper）+ `WorkflowStep` record。
    - `streamToolAnswer(spec,...)` 改名重构为 `streamChunks(full,...)`（工作流已串行跑完，切片逻辑复用）。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务**让新列自动补上并加载新 class。
- 兼容性核对结论（用户问"是否影响路由/连续对话/记忆"）：
  - 未配置 workflow 的智能体：代码路径完全不变（`runWorkflowIfConfigured` 直接穿透到原 `buildRequest`），路由/追问/记忆/工具行为零影响。
  - 前端按字段名发 JSON，不含 workflow → 收到 null → `applyFields` 跳过 → **编辑已有智能体不会清空 workflow**（向后兼容）。但目前页面尚无 workflow 编辑框，需走 API/DB 配置。
  - `streamToolAnswer` 已无引用（改造为 `streamChunks`）；`new UpsertAgentRequest` 仅 AgentController 一处，已补 `req.workflow()`。
- 自查修掉一处不一致：长期记忆原本只在第 1 步注入（`i==0`），改为**所有步骤都注入**——用户偏好应贯穿整条流水线（否则翻译步骤看不到"用英式英语"这类偏好）。已确认参数仍只在第 1 步注入（后续步骤以上一步产物为输入，无关参数是噪声）。
- 复用的既有能力：工作流 Agent 自己若声明 paramSchema，缺参时会先走 `decideClarify` 追问（如"查天气并翻译成英文"缺城市 → 追问城市再执行整条链）。

## 动态 Planner 替代手动工作流（2026-08-28 16:22）
- 用户反馈：手动配置工作流步骤"对用户不友好"，要求改用**动态 Planner**（运行时由 LLM 规划多智能体步骤）。
- 核心思路：保留 Agent 作为原子能力；新增**规划模式会话**（conversation.planner=1），不再需要预配置步骤。每次对话由 `PlannerService` 用独立无记忆 ChatClient 让用户目标 + 可用 agent 清单 → 产出顺序计划 JSON `{"steps":[{"agentCode","instruction"}]}`，再由 `ChatService` 顺序执行（前一步输出作下一步输入）。用户零配置、直接描述目标即可。
- 改动：

  - `ConversationService`：`createConversation(agentId,agentName,planner)` 重载 + `createPlannerConversation()`（标题"🧭 智能规划"）。
  - `ConversationController`：建会话支持 `planner:true`（与 agentId/workflowId 互斥）；列表/返回带 planner 字段。
  - 新增 `PlannerService`（plan 产出 PlanStep 列表，Hutool 解析，去 ```json 围栏，失败回退空列表）。
  - `ChatService`：注入 PlannerService；`chat()/stream()` 顶部检测 planner 会话 → `handlePlannerConversation`；抽取共用 `executeSteps(List<StepSpec>,...)`，`runWorkflow` 与规划器复用同一执行逻辑（记忆/工具挂载语义一致）；规划无结果/智能体不存在 → `answerDefault` 回退普通助手。

## 修复：规划模式会话记忆污染（2026-08-28 17:05）
- 现象：规划模式多步执行后，chat_message 里存的「用户消息」是脏的（变成「指令 + 上一步输出」合成串），用户原话丢失；maybeMergeMemory 还会把脏数据摘要进长期记忆，越错越深。
- 根因：`executeSteps` 仅最后一步用带记忆的 `chatClient`，而最后一步 user 输入就是合成串，记忆 Advisor 把该合成串当作用户消息落库。
- 修复：
  - `ChatService` 注入 `ChatMemory` bean（DbChatMemory）。
  - `executeSteps` 所有步骤统一改用 `internalChatClient`（不挂记忆 Advisor），执行期间绝不写库；最后一步额外注入 `buildRecentHistoryText()`（读 chatMemory.get 窗口内历史）以保持上下文连贯。
  - 新增 `savePlannerExchange(conversationId, userMsg, reply)`：执行完后用 `chatMemory.add(...)` 显式写入「用户原话 + 最终回复」整对，记忆才正确。
  - `answerDefault`（无计划/智能体不存在的回退）仍走 `chatClient` 记忆 Advisor（传入原始 message），本身正确，无需改。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务**验证。
- 复盘：凡「串行多步、只有最后一步带记忆」的编排，绝不能让记忆 Advisor 落库合成输入；应执行期不写、结束后补写真实问答对。
