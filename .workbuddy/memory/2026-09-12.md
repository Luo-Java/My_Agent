## ChatMemory 装配机制（答疑，未改代码）

**问题**：`ChatMemory` 接口下有多个实现，怎么确定用的是自定义的 `DbChatMemory`。

- **唯一装配点**：`config/ChatMemoryConfig`（`@Configuration`）→ `@Bean @ConditionalOnMissingBean(ChatMemory.class)` 手动 `new DbChatMemory(conversationService)`。
  `DbChatMemory` 类上**只有 `@Slf4j`、无任何 stereotype 注解**，所以它只能靠这个 @Bean 注册——全项目搜 `implements ChatMemory` 仅此一处。
- **Spring AI 2.0 自带竞争实现**：classpath 内确有 `spring-ai-autoconfigure-model-chat-memory-2.0.0.jar`，其中
  `ChatMemoryAutoConfiguration`（`@AutoConfiguration` + `@ConditionalOnClass({ChatMemory, ChatMemoryRepository})`）定义两个 @Bean，
  **均带 `@ConditionalOnMissingBean`**：`chatMemoryRepository()`→`InMemoryChatMemoryRepository`、`chatMemory(repo)`→`MessageWindowChatMemory`。
- **为什么胜出的是我们**：Spring Boot 保证 `@AutoConfiguration` 在所有用户 `@Configuration` **之后**处理 → `dbChatMemory` 先注册 →
  自动配置的 `chatMemory` 条件不成立被跳过。**副作用**：`InMemoryChatMemoryRepository` 仍会被注册（我们不提供 `ChatMemoryRepository`），
  成为**无人消费的孤儿 bean**（无害，但别处若注入 `ChatMemoryRepository` 会意外拿到内存版）。
- **坑（勿踩）**：不要在任何其他地方再定义 `@Bean ChatMemory`。两个用户配置类之间的处理顺序不确定，
  `@ConditionalOnMissingBean` 可能双双通过 → 注册两个同类型 bean → 启动 `NoUniqueBeanDefinitionException`。
- **运行时自证办法（无需改代码）**：启动加 `--debug`，在 CONDITIONS EVALUATION REPORT 中搜 `ChatMemoryAutoConfiguration#chatMemory`，
  应显示 `Did not match: @ConditionalOnMissingBean ... found beans of type 'ChatMemory' dbChatMemory`。

## 全局字体清晰度修复（用户反馈「智能体 / 知识库页面字体太模糊」）

**三个根因**（全部在 `style.css`，纯前端、无 Java 改动）：
1. **小数像素字号**（最直接的模糊源）：知识库区有 6 处 `12.5px` / `11.5px`（`.kb-file-item`、`.kb-empty-tip`、
   `.kb-file-meta`、`.kb-upload-strategy` 等）。小数 px 在 Windows 上触发**亚像素渲染**，笔画被重新采样 → 发虚。
   → 统一 `12.5px`→`13px`、`11.5px`→`12px`。
2. **辅助色对比度不足**：`--text-soft: #8a93a3` 对白底对比度仅约 **3:1**，低于 WCAG AA 正文要求的 4.5:1。
   → 改为 `#5f6b7d`（约 5.5:1）。顺带把两处硬编码浅色也加深：`.tool-search input::placeholder` `#aab3c2`→`#98a2b3`、
   `.tool-group-name em` `#9aa4b5`→`#6b7688`。
3. **最小字号过小**：存在 10px / 11px 文字。→ 全局 `11px`→`12px`、`10px`→`11px`（`replace_all`）；
   另把 `.agent-card-desc` 12px→13px（智能体卡片描述是主要阅读内容）。

**附加**：`body` 字体栈改为 Windows 友好
`-apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei UI", "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", sans-serif`
（Windows 拉丁走 Segoe UI、中文走 **Microsoft YaHei UI**，比旧版 Microsoft YaHei 更清晰），并加
`-webkit-font-smoothing: antialiased; -moz-osx-font-smoothing: grayscale;`。

**排查结论（供日后复用）**：已确认 CSS 中**无** `transform: scale()` / `zoom`（缩放会导致文字重采样发虚）；
`font-weight: 500/600` 在只含 Regular+Bold 的雅黑上按规范回退到 400/700，**不会**触发伪加粗模糊。

**验证**：MVN_EXIT=0 / BUILD SUCCESS（无代码告警）。**待用户**：浏览器 Ctrl+F5 强刷。

1. **粗排召回**：`agent.rag.recall-k`(默认 20) 条，下限放宽到 `recall-min-score`(0.10)。召回阶段「别漏」，判相关性交给精排。
2. **精排**：新建 `infrastructure/rerank/RerankService` —— Spring AI 2.0 **没有 rerank 抽象**，且 DashScope text-rerank
   **不在 OpenAI 兼容路径下**（`/api/v1/services/rerank/text-rerank/text-rerank`），故用 Hutool `HttpRequest` 手写
   （与 `ChromaConnection` 一致），api-key 复用 `spring.ai.openai.api-key`。按 `rerank-min-score`(0.20) 过滤、取 `top-k`(3)。
   - **降级**：未开启/无 key/超时/非 200/结构不符 → 返回 `null` → 回落「向量分降序 + `min-score`(0.25) 截断」= 改造前行为。
   - **精排成功但候选全被滤掉 → 直接返回空，不退回向量分**：既然精排判定都不相关，塞低分向量块只会污染回答。
   - **阈值是两套尺度**：rerank relevance_score(0~1) 与余弦相似度不可互相套用，配置项独立。

2. **`MessageChatMemoryAdvisor.before()` 会写库**：源码第 4 步 `chatMemory.add(conversationId, userMessage)`，`after()` 再写 assistant 消息，即「先读库、再写库」。**这否决了「请求级缓存整个 get 结果」的方案**：缓存必须在 add 时失效，而 add 紧跟在 get 之后 → 几乎无收益；若用 ThreadLocal 且清理遗漏（boundedElastic 线程复用），下一轮会静默拿到上一轮历史（丢本轮用户消息）。风险 >> 收益（省一次 200 条查询 ≈ 数毫秒）。**故不做，理由已记档。**
   - 真实的「重复读」只有一处：同一轮内 `buildHistoryContextText`（路由上下文）与 advisor `before` 各读一次**相同的** `getRecentHistory(200)`，间隔内无写入 → 理论可复用，但收益仅毫秒级，同样不做。

### 改动清单
1. **前置链并行预取（#5，本轮主收益）**：一轮首字前是「智能路由 → 参数抽取 → 查询改写」三个串行模型往返，**改写只看用户原话 + 会话历史、与另两段零依赖** → 提到本轮最前并发执行，**省掉整整一个模型往返**（≈0.5~2s）。
   - `ExecutorConfig` 新增 `roundPrefetchExecutor`（核心 4 / 最大 8 / 队列 256 / 前缀 `prefetch-`，`waitForTasksToCompleteOnShutdown=false`）。
   - `ChatComposer.prefetchRetrievalQuery(cid, message, conv)`：仅 `ragOn(conv)` 时提交，否则返回 `null`（零额外调用）；线程池拒绝记日志返回 null。
   - `ChatComposer.resolveQuery(...)`：join 预取，**超时 `REWRITE_JOIN_TIMEOUT_SECONDS=10` / 中断 / 异常一律回退用户原话**；传 null（未预取）→ 同步改写（= 改造前行为）。**预取只加速、不承担正确性**。
   - `ChatComposer.buildRequest` 增 8 参重载（末尾 `CompletableFuture<String> prefetchedQuery`），原 7 参版委托传 `null` → 其他调用点（规划 `buildDefaultRequest`）**零改动**。
   - `AgentRoundHandler.handle` 最前发起预取，正式回答处 `buildRequest(..., prefetchedQuery)` 消费。
   - **代价（刻意接受）**：本轮若走「参数追问」分支，预取结果作废（浪费一次很轻的改写调用）。
   - **规划模式不预取（有意）**：规划大多不回退通用助手，预取浪费概率高；`buildDefaultRequest` 保持同步改写。
2. **参数抽取历史有界化（#7 的可行部分）**：`ParamFillingService` 原用 `conversationService.getHistory`（**全量 selectList**，长会话每轮无界拉取，而 AI 记忆本身只按 token 预算读窗口）→ 改 `getRecentHistory(cid, HISTORY_SCAN_LIMIT=50)`（`decideClarify` + `lastClarifyQuestion` 两处）。50 条充分覆盖其尾部语义（追问段 ≤ `MAX_CLARIFY=3` 轮 = 至多 6 条；参数窗口 12 条）。类注释「全量重放」措辞同步更正。
