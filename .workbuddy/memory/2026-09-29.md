## 会话与用户绑定（按用户隔离）
- 需求：会话原本与用户无关，要求「每个用户只能看到自己的对话」。
- DDL：`conversation` 加 `user_id BIGINT DEFAULT NULL`（关联 `sys_user.id`）+ `INDEX idx_user`；同步 `sql/schema.sql`（建表）与 `sql/alter.sql`（存量库 ADD COLUMN / ADD INDEX，幂等）。存量会话 `user_id=NULL`，不归属任何用户，对所有人不可见；如需归属可 `UPDATE conversation SET user_id=<ID> WHERE user_id IS NULL`。
- 服务层 `ConversationService` 全面归属化：`createConversation(..., userId)` 写入 `user_id`；`listConversations(userId)` 按 `user_id` 过滤；`renameConversation` / `updateRagEnabled` 把 `user_id` 塞进 UPDATE 的 WHERE 并「影响 0 行 → 404」；`updatePlannerSwitch` / `deleteConversation` 先 `requireOwned`；`ensureConversation(id, userId)` 不存在则带 `user_id` 补建、属于他人则 404。新增 `requireOwned`（必须存在且归属本人，否则 404）与 `checkAccess`（仅「存在且非本人」时 404，不存在放过、留给 ensureConversation 建）。
- 关键坑：**`AuthContext` 是 ThreadLocal，`ChatService.stream/resume` 的执行体跑在 `boundedElastic` 上，异步链路里读不到**。故 userId 必须在 Controller 的 HTTP 线程用 `AuthContext.require().id()` 取出后**当参数往下传**（`chat/stream/resume/ensureConversation` 全线加 `Long userId`）。`ConversationController` 是同步的，可以直接 `AuthContext.require()`。
- 流式接口的越权：`stream/resume` 里若让异常在异步体抛出，只会变成 SSE 里一条 `error` 事件、拿不到 404。故在 `ChatController` HTTP 线程先 `conversationService.checkAccess(cid, userId)` 前置挡掉 → 真正的 404。
- `ChatController.resolveConversationId` 的空值兜底从公共 `"default"` 改为按用户派生 `"default-" + userId`：否则两个用户会撞进同一个 ID（后者被判 404）。
- 越权响应一律 404 而非 403：与「不存在」不可区分，避免用会话 ID 探测他人会话是否存在。
- 未覆盖（已向用户点明）：`/api/trace`（含 `agent_trace.user_message`）、`/api/cost/summary` 是按 conversationId / 全量的可观测旁路，仍可跨用户读取；如需收敛可加 `@RequireRole(ADMIN)` 或同样按归属过滤。
- 验证：`bash .workbuddy/memory/run_mvn.sh` BUILD SUCCESS。

## 修复规划模式「前驱产出无界拼接」缺陷（新增 PlannerProperties）
- 缺陷：`PlannerRoundHandler.buildStepInput` 把前驱产出全量 `sb.append(depOut)` 拼进下一步的 user 消息，**无任何长度上限**。多步规划中第 N 步会带上全部 N-1 个前驱的全文，输入随「步骤数 × 单步产出长度」**无界增长**，最终击穿模型上下文 —— 且是**静默失败**（模型自行丢弃中间内容，不抛错、日志无痕，表现为「答得莫名其妙」却查不出原因）。
- 排查结论（先确认边界再动手）：附件侧**不是**洞 —— `AttachmentService` 早有 `MAX_INLINE_CHARS = 30000` + 截断标注，`DocumentParserService` 有 `MAX_TEXT_CHARS = 500_000`；会话历史侧也不是（`DbChatMemory.truncateOverlong` + 窗口条数下限）。**真会爆的只有前驱产出这一条，因为它是累加的**，其余都是单条 / 单窗口有界。
- 修法：新增 `org.luo.ai.properties.PlannerProperties`（`agent.planner.*`），配额 = `min(upstream-max-chars, upstream-total-chars / 前驱个数)`（默认 4000 / 12000）。前者防「单个前驱特别长」，后者防「前驱个数特别多」，两者同时约束才有上界。`perUpstreamChars(count)` 用 `Math.max(1, ...)` 兜住「前驱数极多时均分算成 0 → 把上游产出整段丢光」。
- 三个刻意的设计决定：① **不支持关闭**（非正数一律回落默认，不留「置 0 恢复原行为」的开关）—— 无界增长是缺陷不是可选项，留个开关只会让缺陷悄悄回来；② 保留**前段**而非尾段 —— LLM 产出通常「结论在前、展开在后」，前段信息密度更高；③ 截断必带**显式省略标注 + WARN**（`…（该步骤产出过长已截断，后续省略 N 字符；不要基于被省略的内容作答）`）—— 静默截断会把「模型答偏」变成查不出原因的谜。
- 顺手补的一处：多前驱拼接原先没有任何来源标识，各前驱产出首尾相连，模型分不清哪段来自哪一步；现每段前加 `[步骤 N 的产出]` 头。这是让省略标注能被正确归属的前提（否则标注会被读成上一段的内容）。
- **配额只作用于「注入下一步的输入」**：不影响 `task_step.output` 落库、也不影响最终回复 —— 用户看到的始终是完整产出。这是设计意图，后续重构别把截断上移到产出侧。
- 落地清单：新建 `PlannerProperties.java`；`PlannerRoundHandler` 构造器注入 + `buildStepInput` 改造 + 新增 `truncateUpstream`；`MyAgentApplication` 的 `@EnableConfigurationProperties` 登记；`application.yaml` 紧邻 `agent.memory` 加段（含「不支持关闭」的注释）；README 配置示例 + 「关键机制」表各补一条。
- 验证：`bash .workbuddy/memory/run_mvn.sh` BUILD SUCCESS。配额逻辑手工推演 count=1/3/5/10/100/20000 → 4000/4000/2400/1200/120/1，合计恒 ≤ 12000，无除零 / 归零分支。**未做运行期实测**（不启动应用，按约定由用户在 IDE 自启）。

## 子 agent 上下文隔离（规划步骤 system 分三档）
- 起因：用户按上一轮给出的方向编号选择「做 4 和 8」，其中 ⑧ = 子 agent 上下文隔离。原状是所有规划步骤共读同一会话的长期记忆（`summary`/`core_facts`）与同一近期窗口，中间步骤被会话级摘要带偏。
- 改法（`PlannerRoundHandler.runStep`，system 拼装一处开关）：**首层**（`idx==0`）吃「已确认参数 `paramBlock`」、**末层**（`isLastStep`，汇总步）追加近期窗口 `historyContext`、**中间步骤默认不注入长期记忆**。即 `boolean isolateMemory = !isLastStep && idx != 0 && plannerProperties.isolateMiddleStepsOn();`。
- 为什么首层与末层例外：首层此时还没有任何前驱产物、它承接的是「用户原始目标 + 已确认参数」；末层负责把各步收口成一条完整回答，需要会话上下文。只有中间步的活是「拿前驱产物做自己那一段」，长期摘要对它基本是噪音。
- **RAG 资料刻意不参与隔离**：`buildKbContext` 每步照旧执行 —— 各步 query 不同、按各自需要检索；「检索资料」与「会话记忆」不是一回事，隔的是后者。
- 配置：`PlannerProperties` 加 `isolateMiddleSteps`（`agent.planner.isolate-middle-steps`，默认 true，`isolateMiddleStepsOn()` 访问器），与上一轮的配额同属一个 properties 类。

- 起因：`prompts.yaml` 有 11 个模板（路由判定、参数抽取、查询改写、规划、汇总…），改动完全靠手感；`agent_trace` 已记录路由来源/计划/工具调用/token，只缺「跑批 + 断言」这层壳。零侵入现有链路。
- 后端全链路落地：`EvalProperties`（`agent.eval.*`）/ `EvalCase` / `EvalCaseResult` / `EvalBatchResult` / `EvalBatchSummary` / `EvalCompare` / `EvalResult` 实体 / `EvalResultMapper` + `mapper/ai/EvalResultMapper.xml` / `EvalService` / `EvalController` / `ExecutorConfig` 加 `evalExecutor`（core 4 / max 8 / queue 128，不等待关闭）/ `eval-cases.yaml`（ROUTE 8 条 + PLAN 5 条，用真实 agentCode A001~A004）/ DDL 同步 schema+alter。

- **三态分开是关键设计**：`passed` / `failed`（质量问题）/ `configError`（用例写错，如断言引用了不存在的 agentCode）。分类靠 SQL 聚合 `failed` 只算 `passed=0 AND config_error=0`，`config_errors` 单列。混算会让用例维护失误被误读成「模型变笨」。
- `EvalBatchSummary` 写作 **bean 而非 record**：它充当 MyBatis 结果投影，bean 的 setter 映射不依赖 `-parameters` 编译条件。其余 DTO 仍是 record。
- 用例集解析用 Hutool `YamlUtil` + `JSONUtil`，**显式 UTF-8 Reader**（`YamlUtil` 无 `load(InputStream)` 重载，且中文用例名跟平台编码会读成乱码）；解析失败抛 400，不静默变「0 条用例」。

- 清理旧批次 SQL（保留最近 20 批）**必须套派生表**：MySQL 不允许 `DELETE` 的子查询直接引用被删的表（报 1093）。
