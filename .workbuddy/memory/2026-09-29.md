## 会话与用户绑定（按用户隔离）
- 需求：会话原本与用户无关，要求「每个用户只能看到自己的对话」。
- DDL：`conversation` 加 `user_id BIGINT DEFAULT NULL`（关联 `sys_user.id`）+ `INDEX idx_user`；同步 `sql/schema.sql`（建表）与 `sql/alter.sql`（存量库 ADD COLUMN / ADD INDEX，幂等）。存量会话 `user_id=NULL`，不归属任何用户，对所有人不可见；如需归属可 `UPDATE conversation SET user_id=<ID> WHERE user_id IS NULL`。
- 服务层 `ConversationService` 全面归属化：`createConversation(..., userId)` 写入 `user_id`；`listConversations(userId)` 按 `user_id` 过滤；`renameConversation` / `updateRagEnabled` 把 `user_id` 塞进 UPDATE 的 WHERE 并「影响 0 行 → 404」；`updatePlannerSwitch` / `deleteConversation` 先 `requireOwned`；`ensureConversation(id, userId)` 不存在则带 `user_id` 补建、属于他人则 404。新增 `requireOwned`（必须存在且归属本人，否则 404）与 `checkAccess`（仅「存在且非本人」时 404，不存在放过、留给 ensureConversation 建）。
- 关键坑：**`AuthContext` 是 ThreadLocal，`ChatService.stream/resume` 的执行体跑在 `boundedElastic` 上，异步链路里读不到**。故 userId 必须在 Controller 的 HTTP 线程用 `AuthContext.require().id()` 取出后**当参数往下传**（`chat/stream/resume/ensureConversation` 全线加 `Long userId`）。`ConversationController` 是同步的，可以直接 `AuthContext.require()`。
- 流式接口的越权：`stream/resume` 里若让异常在异步体抛出，只会变成 SSE 里一条 `error` 事件、拿不到 404。故在 `ChatController` HTTP 线程先 `conversationService.checkAccess(cid, userId)` 前置挡掉 → 真正的 404。
- `ChatController.resolveConversationId` 的空值兜底从公共 `"default"` 改为按用户派生 `"default-" + userId`：否则两个用户会撞进同一个 ID（后者被判 404）。
- 越权响应一律 404 而非 403：与「不存在」不可区分，避免用会话 ID 探测他人会话是否存在。
- 未覆盖（已向用户点明）：`/api/trace`（含 `agent_trace.user_message`）、`/api/cost/summary` 是按 conversationId / 全量的可观测旁路，仍可跨用户读取；如需收敛可加 `@RequireRole(ADMIN)` 或同样按归属过滤。
- 验证：`bash .workbuddy/memory/run_mvn.sh` BUILD SUCCESS。

## 移除「访问密钥」（服务级 api-key 闸门）
- 起因：用户提出「AI 对话页顶栏的访问密钥可以去掉了吧，已接入用户登录」。
- 判定依据（不是照做，是先验证）：`app.api-key: ${APP_API_KEY:}` 默认为空 ⇒ 闸门实际是关的；而 `auth.js` 的登录/请求只带 `Authorization`、**不带 `X-Api-Key`**，`ApiKeyInterceptor` 又对 `POST /api/auth/login` **没有豁免** ⇒ 一旦真配上 `APP_API_KEY`，登录接口会被 401 拒掉、用户根本进不来。即该闸门与登录流程**从根本上冲突**，且 `/api/**` 已由 JWT 全覆盖，机器调用同样得先登录，它不再提供额外保护。故整段删除，而非只藏按钮。
- 后端：删 `common/config/ApiKeyInterceptor.java` + `ApiSecurityConfig.java`；`application.yaml` 去掉 `app.api-key` 并把配置注释改成「登录鉴权是唯一闸门」；`JwtSecurityConfig` / `AttachmentWebConfig` / `AttachmentStorageService` / `CostController` / `TraceController` 里对 `ApiSecurityConfig`、`X-Api-Key` 的注释改指 `Authorization` / `JwtAuthInterceptor`。
- 前端：`app.js` 删 `API_KEY_STORAGE` / `getApiKey()` / `X-Api-Key` 注入 / `apiKeySet` / `editApiKey` 及导出（`apiFetch` 保留，只做向 `Auth.fetch` 的转发）；`edu.js`、`user.js` 里**各有一份同样的复制粘贴**也一并删；`chat.html` 删顶栏 🔑 按钮；`style.css` 删 `.key-btn` / `.key-btn-on`；`auth.js` 删 `API_KEY_FAILURE_REASON` 常量与 `isSessionInvalid` 里的显式排除分支（保留 `TOKEN_FAILURE_REASONS` 白名单本身）。顺带确认 `.trace-btn` 自带 `margin-left:auto`，删掉 key-btn 后「追踪」按钮仍会把右侧按钮组推到位。
- **构建必须带 clean**：删源码后 `target/classes` 里仍残留 `ApiKeyInterceptor.class`/`ApiSecurityConfig.class`，不 clean 的话 Spring 启动会照旧扫到并注册它们（删了等于没删）。故本轮跑的是 `mvn -o clean package`（不是默认的 `package`）；已核对 `target/classes/org/luo/common/config/` 与 jar 内均无 ApiKey 相关 class。
- 文档：`README.md`（配置示例、3.1 部署安全、包结构树、顶栏说明、登录说明）、`ARCHITECTURE.md` 鉴权条、`FRONTEND.md` 401 归属条、`MEMORY.md`「包结构」与「鉴权」红线同步。

## chat 顶栏：右侧动作区靠右改由容器负责 + 新增教务系统入口
- 起因：用户反馈「用户名 / 用户管理 / 退出应该放最右边，并加一个跳转教务系统的按钮」。
- 真因（不是审美问题，是布局支点挂错了）：顶栏靠右一直由 `.trace-btn { margin-left: auto }` 撑着，而该按钮是 `v-if="currentId"` —— **无会话（未建会话 / 新开会话）时它不渲染，右侧整组就失去支点、塌回标题旁边**。另 `.cost-btn { margin-left: 8px }` 在文件更靠后，已把成本按钮那份 auto 覆盖掉，等于只有追踪按钮能撑。
- 修法：新增容器 `.header-actions`（`inline-flex` + `gap:10px` + `margin-left:auto` + `flex:none`），把「追踪 / 成本 / 教务系统 / 登录用户区」整套装进去；删 `.trace-btn` 的 `margin-left:auto`、删 `.cost-btn` 的 8px、删 `.auth-box` 在 style.css 里的 `margin-left:8px`（间距统一交给容器 gap）。edu / user 两页的 `.auth-box` 定义在各自 CSS，未受影响。
- 新增教务入口 `<a class="trace-btn nav-link" href="/edu.html">🎓 教务系统</a>`，与 edu 页顶栏既有的「前往 AI 对话 →」互为对称入口；`.nav-link` 只补 `text-decoration:none` + 居中，盒模型复用 `.trace-btn`。
- 验证方式（值得复用）：起 `python -m http.server` 静态服务 → 复制 `chat.html` 为 `static/_check_topbar.html`，注入 CSS 隐藏 `.auth-veil`（未登录时它盖住整页，直接截图只拍到登录框）并按 `?trace=1` 决定是否补一个假「追踪」按钮 → 无头 Chrome `--dump-dom` 取几何探针 + 截图。**关键教训：本轮先靠截图判断，误以为「有追踪按钮时成本/教务没渲染」，实际是图上小胶囊按钮没看清；改用几何探针（getBoundingClientRect + computedStyle.marginLeft）后一次定案**：两种状态下 `.header-actions` 的 `right` 都精确等于 header 内容右界 1464，各子项 `margin-left: 0px`、间距恒为 gap 10px、`docScrollWidth <= innerWidth` 无溢出。
- 截图参数坑：`--force-device-scale-factor=1.5` 会让 **CSS 视口 = window-size / 1.5**，沿用 1440 宽会把顶栏右侧裁掉；要看整行用 scale=1 并把 window-size 放大（或用 2520 宽配 1.5）。
- 验证：`bash .workbuddy/memory/run_mvn.sh` BUILD SUCCESS；jar 内 `static/chat.html` 含 `header-actions`/`nav-link`、无临时检查页残留。

## 顶栏用户区统一为「用户名 → 下拉菜单」

- 做法：**收敛到 auth.js 一份实现**。四页顶栏只留 `<span data-auth-nav></span>`，`renderNav` 渲染「用户名 + ▾」触发器 + `.auth-menu` 下拉（个人信息 / 修改口令 / 用户管理（仅 ADMIN）/ 分隔线 / 退出登录）。为此删掉 chat/edu/user 三页各自的 `.auth-box` / `.auth-user` / `.auth-entry` **及其在 style.css / edu.css / user.css 里的样式**（此前同一份外观抄了三遍），以及三页 JS 里的 `authUser/authName/authIsAdmin/authLogout` 与导出。新增 CSS 只在 auth.css（`.auth-user-trigger` / `.auth-menu*` / `.auth-info*`）。edu 页 `.edu-topbar-right` 因失去 `.auth-box` 的 margin-left 而补 `gap:8px`。
- 后端无需改动：`GET /api/auth/me`（个人信息）与 `POST /api/auth/password`（改密）早已存在；口令强度校验在 `PasswordHasher.requireValid()`（6~64 位、非空），前端即时校验按同一口径写，**不动后端**。

- 三个代码坑（都实测确认）：`[hidden]` 必须显式写 `.auth-menu[hidden]{display:none}`（否则被 `.auth-menu` 自身的 display 声明盖掉）；触发器与菜单项的 click 都要 `stopPropagation`，否则被 document 上的「点空白收起」监听点开即关；账号弹框**与登录框各持一个 veil 单例**，共用会互相顶掉。
- 验证：静态服务 + 无头 Chrome。CDP 精确截图（`Page.captureScreenshot` 带 clip，比全页截图清晰得多）看到四页顶栏都只剩「业务入口 + 用户名 ▾」；`Runtime.evaluate` 实测菜单开关（点触发器展开/收起、点空白收起、Esc 收起，aria-expanded 同步）与改密四项前端校验文案全部正确。
- 一个过程教训：起先只看命令行 `--screenshot` 的全页图，误以为 chat 顶栏的「成本 / 教务系统」两个按钮没渲染，准备去改代码；改用几何探针（`getBoundingClientRect` + `computedStyle`）后证明三个元素都 `vis=visible / op=1`、位置连续 —— **是小图上深色胶囊按钮没看清**。截图看不清时先上探针，别急着改代码。
- 验证：`bash .workbuddy/memory/run_mvn.sh` BUILD SUCCESS；脚手架（4 个 `_chk_*.html` + 两个 CDP 脚本 + 中间截图）已全部删除，static 下无残留。

- **为什么不塞进 auth.css**（那里已在管 login 弹框 + 顶栏用户区，离得最近）：auth.css 是 `auth.js` 动态 `ensureCss` 注入的，靠它会出现「首屏按钮先无样式、随后才补上」的一帧闪烁；静态 `<link>` 是显式依赖，也更符合「样式在哪个文件」的可预期性。
- 复用注意：`.nav-pill` **不带 margin**（chat 页靠右由 `.header-actions` 的 `margin-left:auto` + `gap` 负责）。
- 验证（本轮新手法，值得照用）：给 `serve_preview.py` 加了通用探针注入 `?__js=<名称>`（注入 `tools/<名称>.js`，结果写 `<pre id="__probe">`）+ 新增 `.workbuddy/tools/verify_topbar.py`。三页实测 `.nav-pill` 的 padding（5px 12px）/ 圆角（999px）/ 字号（13px 500）/ 行高（13px）/ 文字与底色与描边色 / 高度（25px）**逐字段一致**，`<a>` 与 `<button>` 两版一致，右对齐间距 20px（chat 页预览态 73px 是因为预览环境用户名区渲染成「登录」按钮的占位差异，非本轮改动引入）。
- 两个工具坑（都已写进 `TOOLING.md`）：① `subprocess` 调 Chrome **必须显式带 `--dump-dom`**，只给 URL 会 rc=0 + stdout 0 字节，看着像白屏；② 探针脚本注释里写了 `<pre id="__probe">`，注入后会被一起 dump，非贪婪正则从注释处开始匹配会把脚本源码吞进候选 → 解析要**从最后一个 `{"page"` 处截断**。③ 起服务别用 `命令 &`（随 shell 退出被回收，`serve_preview.py` 要用 run_in_background 直接跑）—— 本轮先误判成「user.html 页面特别」（实为服务已死、代理回 502）。
