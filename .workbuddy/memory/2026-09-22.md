## PageResult 增加 of(IPage, List) 重载（自定义分页返回 List 形态）

用户手改 Teacher 链为「Mapper 返回 `List`、Service 返回 `PageResult`、手动 `PageResult.of(page, list)`」后编译不过（缺重载），本轮补齐。

### 改动
- `PageResult.of(IPage<T>)` 改为委托 `of(p, p.getRecords())`；**新增 `of(IPage<T>, List<T>)`**。
- `TeacherController` 去掉多包的一层 `PageResult.of(...)`（Service 现直接返回 `PageResult`）。
- 清理 3 处失效 `import IPage`（TeacherMapper / TeacherService / TeacherServiceImpl）。
- `mvn package` BUILD SUCCESS；`javap` 核对：`of` 两个重载、`page` 返回 `PageResult<TeacherVO>`、`getTeacherPage` 返回 `List<TeacherVO>`。

### 关键结论（MP 自定义分页）
- Mapper「参数带 `IPage`、返回 `List`」是 MP 官方支持的自定义分页写法：分页插件仍查 count 并把 `total`/`pages` 写回**入参 IPage**，但**不回填 records**（返回 List 时 `page.getRecords()` 为 null）→ 必须用 `of(page, list)` 显式传列表。
- 返回 `IPage` 时（如 `ScoreMapper.selectScoreDetail`）records 由框架回填，用单参 `of(ipage)` 即可。

## 表格列宽回归：`th{width:1%}` 让数据全挤到左边（用户反馈）

上一轮为解决「性别列被摊到 200+px」加的 `.edu-table thead th{width:1%}` + `th:last-child{width:auto}`（意图：多余空间全给操作列）**矫枉过正**：auto layout 下非末列被压到 min-content、操作列变成一张巨大空白列，10 列数据全挤在卡片左侧，右侧一大片空。

## 16:10 登录成功后又被要求登录：先让 401 说出原因，再堵三个坑

用户报「登录成功后进入页面又让登录」（附 DevTools 截图，框里只有一句「登录状态已失效，请重新登录」）。没有服务端日志、没有可复现环境，先把「服务端到底在拒什么」变成可读证据。

### 排查链（每条都是可复核的硬证据）
1. **截图里 401 响应体 `Content-Length: 58`** 精确对应 `{"code":401,"message":"登录已失效，请重新登录"}`（UTF-8 手算 23 + 11×3 + 2 = 58；同族候选：`账号不存在或已停用`=70、api-key=65、`RestResult`+data=64）→ 服务端走的是 `parseUserId` 返回 null 那条分支（凭证**缺失/不认/过期**），既不是「账号停用」也不是 api-key。
2. **用 target/classes 里的真实类跑往返**（`JwtProperties` + `JwtTokenService` + 配置里的密钥 + Hutool 5.8.38，classpath 只加 hutool + slf4j-api）：`parseUserId=1`；同密钥「重启」后仍为 1；换密钥 → null。载荷形状 `{"iss":"my-agent","sub":"1","username":"admin","expMs":<now+12h>}`，`tokenLen=173`、`expireSeconds=43200` → **正常配置下服务端逻辑没问题**。
3. **`javap -v` 看 `JwtProperties` 构造器**：`enabled=true`、`secret=""`、**`expireMinutes` 没有初始值（int 默认 0）**、`@ConfigurationProperties(prefix="app.jwt")`。→ **一旦 `app.jwt.*` 没绑上，拦截器照样是开的（enabled 默认 true），而 TTL=0 会让 token「签发即过期」**，症状与原话完全一致，且不抛任何异常 —— 这是个静默地雷。
4. **放大用户截图里的 Authorization**（JDK ImageIO 写了个裁剪放大工具）读出的载荷是 `expMs ≈ 签发时刻 + 12h`（≈43171s）→ 那一份 token 的 TTL 是正常的、形状与当前代码一致 → 那次 401 更像「凭证没到达服务端 / 不被认」，而不是过期。服务端已证明能认自己签的 token，所以**剩下两种可能正好靠新的 `reason` 字段一次区分**：`NO_TOKEN`（头没到）与 `BAD_SIGNATURE`（密钥换过）。

### 改动
- 新增 `org.luo.system.security.TokenCheck`（record + 嵌套 `TokenStatus`：`OK/NO_TOKEN/MALFORMED/BAD_SIGNATURE/MISSING_EXPIRY/EXPIRED/NO_SUBJECT`）。
- `JwtTokenService`：`parseUserId(String)` → **`verify(String)` 返回 `TokenCheck`**（原因显式化）；新增 `resolveExpireMinutes(int)` 兜底（≤0 → WARN + 回落 720）；构造期 INFO 打出生效 TTL（`登录鉴权已启用：token 有效期 720 分钟`）。
- `JwtAuthInterceptor`：401 响应体加 `reason`，按状态给不同 `message`（`未登录，请先登录` / `登录已过期，请重新登录` / `登录凭证无效，请重新登录`），并落 **WARN**（含 method + URI + status）；403 补 `reason=ROLE_DENIED`；`reject()` 加 reason 形参。
- `auth.js`：新增 `failureMessage(resp, fallback)` —— **用 `resp.clone()` 读 401/403 的 `message`**（不消费调用方要读的 body）+ `reason` 进 `console.warn`；`guardNavigation` / `requireLogin` / `Auth.fetch` 三处提示改为「服务端说什么就显示什么」，拿不到才回落 `EXPIRED_MESSAGE`。
- `auth.js` 竞态保护：`Auth.fetch` 的 401 分支加 `if (token && token !== Auth.getToken()) return resp;` —— **旧凭证的延迟 401 不得清掉刚登录拿到的新 token**（否则表现正是「刚登录成功又被要求登录」）。
- `auth.js` 防锁死：`openLoginForPage()` 若已有框（`veil`）不会再触发 `onMounted`，先 `unlockPage()`，否则页面永久停在「正在校验登录状态…」。
- `README.md`：新增「拒绝原因可区分」条目（reason 清单）、「有效期」条目（非法值→WARN+720 的成因与症状）、`JWT_SECRET` 显式空串会覆盖 `${JWT_SECRET:默认值}` 的坑。

## 16:15 「带 charset 的请求都 401」证伪 + BAD_SIGNATURE 定案

用户线索两条：「`Content-Type: application/json;charset=UTF-8` 不一样，带了 `;charset=UTF-8` 的都返回 401」，随后给出服务端日志 **`拒绝 GET /api/agent：BAD_SIGNATURE`**。

### 结论一：charset 与鉴权无关（红鲱鱼，已证伪）
- **请求侧**：全站 JS（`app.js`/`edu.js`/`user.js`/`auth.js`）设的都是 `Content-Type: application/json`，**没有一处带 charset**（`grep charset=UTF-8` 只命中 `lib/echarts.min.js`）。
- **实测对照**（同一 token 打 `POST /api/edu/semesters/page`）：`application/json` → 200；`application/json;charset=UTF-8` → **200（完全相同）**；`text/plain;charset=UTF-8` → 500（媒体类型不支持却落到通用兜底）；无 token → 401。⇒ charset 不参与鉴权。
- **用户看到的差异其实是响应头形状**：`curl -i` 对照 —— 200 响应 `Content-Type: application/json`（Jackson），401 响应 `Content-Type: application/json;charset=UTF-8`（拦截器手写：`setCharacterEncoding` 让 Tomcat 追加 charset）。「带 charset 的都是 401」是**结果**而非原因。

### 结论二：BAD_SIGNATURE = 浏览器留着旧密钥签的 token
- `probe_auth.py` 对**真实服务**实测：现场 login 拿到的 token → `GET /api/auth/me` 200、`GET /api/agent` 200；把 token 末位改成 `A` → 401 `BAD_SIGNATURE`（精确复现用户日志）。⇒ **当前进程签发/校验自洽**，被拒的那份必然来自另一把密钥。
- **生效密钥 = 仓库默认值**（`secret_probe.py`：用 yaml 里的 64-hex 默认值做 HMAC-SHA256 比对 → `True`）；`JWT_SECRET` 在本机用户级/机器级环境变量里都**没有**设置，pom 里也**没有 devtools**。⇒ 密钥是固定的，重启不会换 ⇒ `BAD_SIGNATURE` 只可能是「更早的、密钥还没固定时签发的 token 还躺在 localStorage 里」，重新登录一次即消失。
- 读取 `application-local.yaml`（含口令/API Key）与 `JwtProperties.java` 的两处工具调用被用户**拒绝共享** —— 未重试、未绕过；结论改用「HMAC 比对 yaml 默认值」这条不涉及本地配置内容的路子拿到。

## 17:40 定案真凶：Hutool `JWTSigner` 单例导致并发验签不可靠（「登录后随便点一下就弹重新登录」）

用户报「你把服务搞崩了，登录上后随便点一下就提示重新登录」，并追问「是否携带 authorization + 为什么登录后马上失效」。**结论：不是前端漏带 token，是后端验签在并发下会随机失败。**

### 定位链（每条都可复核）
1. **前端确实带了 Authorization**：`probe_frontend.py`（本地转发 + 注入探针 + 无头 Chrome）从服务端侧记录每个请求的凭证指纹 —— 同一场景下**指纹自始至终只出现一份**，排除「前端换 token / 漏带」。前端「自踢」也已排除（`token=same`）。
2. **同一份 token 有时 200 有时 401**：`probe_token_concurrency.py` 并发打 `/api/agent`，同一份合法 token 得到 **103×200 + 17×401（reason=BAD_SIGNATURE）**。⇒ 服务端验签结果不确定，与密钥、有效期无关。
3. **最小复现**（`.workbuddy/tmp/ConcurrencyTest.java`，用真实编译产物）：把 `JWTSigner` 存为字段、16 线程 × 100 次——
   `OK=232，BAD_SIGNATURE=1288，MALFORMED=80`（失败率 85%）；改为每次现建 signer 后 **1600/1600 全过**。

### 根因
Hutool `HMacJWTSigner` 内部持有**单个** `javax.crypto.Mac`（**非线程安全**），且其 `verify()` 实现是「用同一个 signer 重新签一遍再比对字符串」。原 `JwtTokenService` 在构造期一次性建好 signer 存成 `private final JWTSigner`，被 Tomcat 并发请求共享 → 互相污染 HMAC 计算 → 同一份合法 token 被随机判 `BAD_SIGNATURE`（偶尔误判 `MALFORMED`）。

### 改动
- `JwtTokenService`：删 `private final JWTSigner signer`，改存 `private final byte[] secret`；新增 `newSigner()`，`issue()` / `verify()` 各自**现建**一个 signer。字段声明前留了实测数据注释（为什么不能提升成字段）。
- `ApiKeyInterceptor`：401 响应体补 `reason: API_KEY_REQUIRED` —— 让「服务级密钥缺失」与「登录态失效」在 401 上可分。
- `auth.js`：新增 `TOKEN_FAILURE_REASONS` 白名单 + `API_KEY_FAILURE_REASON` 显式排除 + `isSessionInvalid()`；新增 `confirmSession()`（**并发合用 in-flight 请求**向 `/api/auth/me` 复核）；`Auth.fetch` 的 401 分支改为「非凭证类 → 保留 token 只提示；凭证类 → 先复核，复核通过不弹不清，复核失败才清 + 弹框 + `leaveGuardedPage`」；新增 `Auth.diagnose()` 控制台自检。
- 文档与注释同步（消除 `BAD_SIGNATURE` 旧解说的事实漂移）：`README.md` 3.1（新增并发验签条目 + 前端 401 归属条目 + `API_KEY_REQUIRED` 说明）、`.workbuddy/memory/FRONTEND.md`（`failureMessage` → `readFailure` 改名对齐 + 新增 reason 白名单 / `confirmSession` / `diagnose` 三条）、`JwtTokenService` 的 `verify()`/`fingerprint()` 注释、`auth.js` 的 `BAD_SIGNATURE` 控制台提示与 `diagnose()` 注释。
