## ParamFillingService.extractParams 全量历史问题修复
- 用户指出 extractParams 补全参数时从"所有历史会话记录"处理不好。
- 确认是真实问题（不只是浪费 token）：
  1. **视图不一致**：主模型链路 `DbChatMemory.get` 用 `MAX_RECENT_TOKENS=1000` 窗口，只喂最近 ~1000 字符；而 extractParams 直接 `getHistory()` 全量 → 抽取器能看到窗口外历史并强行注入"已确认参数"，主模型上下文却没有该来源，易冲突。
  2. **成本 O(n²)**：每轮把全量历史重发给抽取 LLM。
  3. **跨任务参数污染**：参数跨整个会话永不重置。
- 修复（快修，已编译通过）：新增 `windowedHistory(history)` 复用 `DbChatMemory.computeWindowStart` 同一窗口算法，抽取器只取窗口内历史；`countClarifyStreak` 仍用全量（只扫 assistant、开销可忽略）。同步更新类/Javadoc。
- 未做（根治方案，待定）：参数作为跨轮状态持久化、增量抽取最新一轮用户补充，从根上消除 O(n²) 与视图不一致。当前窗口化已解决一致性，但长会话参数只在活跃窗口内有效（与主模型对齐，可接受）。

## 澄清状态跨轮丢失 → 追问回答被重新路由导致 agent 丢失（严重流程 bug 修复）

  - 效果：轮2"深圳"复用天气 agent→抽取到城市→真正查天气，不再空转。

## 追问中切换话题检测（修复"未按追问回答、问了别的问题"缺陷）
- 用户指出上一版 bind/unbind 的缺陷：追问期间把 agent 写死在 `conv.agentId`，用户不按追问回答、问别的问题时，下一轮仍被强制复用原 agent 反复要参数。
- 根因：显式绑定与追问绑定只共用一个 `agentId` 字段，运行时无法区分，导致"允许话题切换"无法只作用于追问绑定。
- 修复方案：
  - 新增绑定来源标记 `agent_bind_source` 字段（VARCHAR）：`EXPLICIT`=用户显式选择（粘住、不解绑）、`CLARIFY`=追问临时绑定（允许切换时解绑）、空=未绑定。
  - DDL：`schema.sql` 建表加列；`alter.sql` 加 `ALTER TABLE ... ADD COLUMN ...`（continue-on-error 兼容旧表）。**关键**：`application.yaml` 的 `schema-locations` 原本只列 `schema.sql`，旧库不会自动补列 → 改为 `schema.sql,alter.sql` 两个都列，确保已存在数据库自动加列（否则 MyBatis 写该列报 Unknown column）。
  - `ConversationService.createConversation(agentId!=null)` 标 EXPLICIT；`bindAgent` 标 CLARIFY；`unbindAgent` 与 `AgentService.deleteAgent` 一并清 source。
  - 落库上移：`ParamFillingService.decideClarify` 不再落库 user+assistant（避免话题切换时误落失效追问）；改由 `ConversationService.saveClarifyExchange` 在 ChatService 确认进入追问且非切换时才落库。
  - `ChatService.chat`/`stream` 加话题切换检测：仅当 `CLARIFY` 绑定且本轮仍缺参时，若 `decision.params` 为空（用户未给原 agent 提供任何参数）→ 视为转向别的话题 → `unbindAgent` 并按 `agentRouter.route(message)` 重路由；若路由到别的 agent 或普通对话则按新话题处理。判定用"是否提供参数"区分"追问回答片段(深圳/明天→继续追问)"与"换了话题(帮我写首诗→切走)"，避免"深圳"这类片段被误判切换。
- 编译通过。重启服务后旧库自动补列生效。

## 移除 ToolSearchToolCallingAdvisor（解决简单天气查询 7 次迭代 / toolSearchTool 被反复调用 4 次）
- 现象：简单天气查询日志显示 ToolSearchToolCallingAdvisor 跑了 7 轮，其中 `toolSearchTool` 被模型单独执行 4 次，真正的天气工具直到第 6、7 轮才调用。
- 根因（读源码确认）：`extractToolNameReferences` 的 `referenceToolNameAccumulation` 默认 true，第 1 次 search 返回的工具**从第 2 轮起就已暴露给模型**，但模型仍继续调 `toolSearchTool`（模型行为，Advisor 无法阻止其调用 search）。ToolSearch 是给"几百个工具塞不进上下文"的渐进式披露设计的，当前只有 3 个天气工具，用它是纯负优化（多 4 次 search 往返 + 延迟）。
- 决策：**移除 ToolSearch 层**（仍满足"AI 自主决定调哪个工具"，且不按 Agent 写死）。`DefaultChatClient` 在检测到无 ToolAdvisor 时会自动注册默认 `ToolCallingAdvisor`，工具直接可调用。
- 用户指出"移除 ToolSearch 后改为全量暴露 = 退回每次对话都加载全部工具"——确为回归。修正：`buildRequest` 中工具挂载**按 agent 门控**——仅当 `agent != null`（路由/绑定到具体 Agent）时才 `spec.tools(toolRegistry.getToolCallbacks())`；普通对话（agent 为空，如"你好"）不挂任何工具。这样既不把工具无谓塞进每次对话上下文，又无 ToolSearch 的 search 开销，AI 仍在 Agent 范围内自主选工具。构造器注释同步更新。编译通过（MVN_EXIT=0）。
- 改动：
  - `ChatService`：构造器移除 `ToolSearchToolCallingAdvisor toolSearchAdvisor` 注入；`defaultAdvisors(memoryAdvisor, toolUsageLoggingAdvisor)`；`buildRequest` 注释更新；删除 `import ...toolsearch.ToolSearchToolCallingAdvisor`。
  - 删除 `ToolSearchAdvisorConfig.java`；`pom.xml` 移除 `spring-ai-starter-tool-search-advisor` 依赖。
  - 顺带修复 `ToolUsageLoggingAdvisor` 会话 ID 显示 `unknown` 的 bug：原读 `request.context().get("conversationId")`，实际 key 是 `ChatMemory.CONVERSATION_ID`（ChatService 第 219 行 `.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))`），改为读该常量。
- 编译通过（MVN_EXIT=0）。**需重启服务**让新编译 class + 依赖移除生效；重启后天气查询应为 2–3 轮（模型直接调 resolveDate→queryWeatherByDate），不再有 toolSearchTool 浪费。
- 注：若未来工具数涨到几十/上百导致上下文膨胀，可重新引入 ToolSearch（保留 `RegexToolIndex` + 配置类即可）。

## # 修复：CLARIFY 绑定下含城市词的新话题被误查天气（2026-08-24 14:32）
- 现象：轮1「今天天气怎么样」→ 路由天气 agent + 追问补全城市（绑定 CLARIFY，正常）；轮2「深圳烧鸡味道怎么样」→ 仍去查深圳天气（错误）。
- 根因：旧话题切换检测放在 `decideClarify` **之后**、且仅当 `decision.question != null`（仍缺参）才触发。轮2 里"深圳"被当成城市参数抽出来 → 参数凑齐 → `question==null` → 切换分支整段被跳过 → 直接走天气回答分支。本质：原判定依赖"是否凑齐参数"，而新话题恰好含城市词会被凑齐，检测进不去。
- 修法：`ChatService.chat()/stream()` 把话题切换**提前到 decideClarify 之前**：对 CLARIFY 绑定会话重新 `agentRouter.route(message)`，按真实意图判断——
  - 命中同一 agent → 继续补全；
  - 命中另一 agent → 转该 agent（解绑）；
  - 未命中(null) → 用新增 `isTopicSwitch(message)`（含疑问词/问号即视为新问题）区分「深圳/明天」(回答片段，继续) 与「深圳烧鸡味道怎么样」(新话题，转普通对话并解绑)。
- `determineAgent` 对绑定会话直接返回绑定 agent 不变；`isTopicSwitch` 为 `ChatService` 新增私有方法（正则匹配 `？?` 及 `吗/呢/怎么样/怎样/如何/怎么/什么/啥/多少/几/为什么/哪些/哪`）。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务**生效。
- 边界：若路由 LLM 把"深圳烧鸡味道怎么样"误路由回天气 agent（reRouted==同 agent），则 `isTopicSwitch` 不会触发（sameAgent 跳过）；依赖路由 LLM 正确返回 `route:false`。属可接受依赖。
- 【升级 14:37】用户质疑"只能靠 isTopicSwitch 语气词区分吗"（正则脆弱：`帮我写首诗`/`我想知道深圳有啥好吃的` 都不含疑问词）。改为**语义化路由决策**，删除 `isTopicSwitch`：
  - `AgentRouter`：`route(message)` 重载为 `route(message, pendingQuestion)`，返回三态 `RouteDecision(Agent agent, boolean continuation)`（none / routeTo / continueTask）。模型输出三选一 JSON：`{"route":true,"agentCode":..}` / `{"route":false}` / `{"route":false,"continue":true}`；prompt 在存在待回答追问时追加上下文（"若本条是对该追问的直接回答→continue；若是新问题即便含相似词→正常路由"）。
  - `ParamFillingService`：新增 `lastClarifyQuestion(conversationId)` 返回最近一条 🔎 追问文本。

  - 注意：record 组件名不能与静态工厂方法同名（`continueTask` 冲突报错），组件名用 `continuation`、工厂用 `continueTask()`。
  - `mvn -o compile` 通过。需重启生效。LLM 调用次数不变（预检本就是一次路由调用）。
