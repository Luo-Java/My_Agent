### 关键实现要点
- 落库时 `task_step.step_index` 存的是「重映射后的 specs 连续下标」，`depends_on` 存重映射后下标；续跑直接按此重建，agent 被删则标 SKIPPED 并 remapDeps 过滤。

## 有界工具循环（工具组合调用）

给 Spring AI 2.0 默认的「无限工具循环」装上刹车，`mvn package` BUILD SUCCESS。

### 关键结论（踩坑后确认的框架机制）
- Spring AI 2.0 的工具调用**天生就是循环的**：`ToolCallingAdvisor.adviseCall` 里 `do...while(isToolCall)`，模型返回 toolCall 就执行工具、把结果拼回 instructions 再调模型，直到不再返回 toolCall。「查表→查数→画图」这类有依赖的多步链本来就支持，无需自己写循环。
- 该循环**默认无迭代上限**，只靠模型自己停止，模型反复调同一工具会死循环。所以「工具组合调用」要做的不是实现循环，而是**给循环装刹车**。
- `ToolCallingAdvisor` 的 bean 来自 `ChatClientAutoConfiguration.toolCallingAdvisorBuilder`（`@ConditionalOnMissingBean`，返回 `ToolCallingAdvisor.Builder<?>`）。覆盖方式 = 提供一个**同类型** `ToolCallingAdvisor.Builder<?>` bean。
- `ToolCallingAdvisor` 提供 `doBeforeCall`（每轮模型调用前触发，返回处理后的 request）与 `doFinalizeLoop`（循环结束触发）两个 protected 钩子，可 override。
- `Prompt.augmentSystemMessage(Function)` 可给 system 追加指令（软刹车用）。

### 新增/修改
- 新增 `properties/ToolCallProperties.java`（`agent.tool-call.*`：max-iterations=10、repeat-threshold=3，compact constructor 兜底）
- 新增 `advisor/BoundedToolCallingAdvisor.java`：继承 ToolCallingAdvisor，ThreadLocal 计数，重写 doBeforeCall 做「轮数上限 + 连续重复检测 + 软刹车（augmentSystemMessage 追加停止指令）」，braked 标记防重复追加，doFinalizeLoop 清 ThreadLocal
- 新增 `config/ToolCallingConfig.java`：提供 `ToolCallingAdvisor.Builder<?>` bean 覆盖默认（内嵌 BoundedToolCallingAdvisorBuilder 子类，override build() 返回有界 Advisor）
- 改 `MyAgentApplication.java`：登记 ToolCallProperties
- 改 `application.yaml`：加 `agent.tool-call` 段
- 改 `README.md`：工具调用节补「有界工具循环」

### 遗留边界（已知取舍）
- 软刹车是「请求」模型停止（追加指令），不强制中断循环；模型若不听话仍会继续调工具，最终靠全局 60s 超时兜底。正常模型遵守指令，99% 场景足够。
- 成本看板：用户已提出但本轮未做（聚焦工具组合调用），下一步待做——agent_trace 已有 prompt/completion/total_tokens + elapsed_ms + tool_calls 字段，落点是 CostService 聚合 + GET /api/cost + 前端看板。

## 成本看板（全量成本口径）

接续上条待办，落地成本看板，`mvn package` BUILD SUCCESS（109→115 源文件，无新增告警）。

### 关键架构决策：独立 `llm_usage` 流水表
用户要求「全量口径」而非 agent_trace 的「回答成本」口径。摸清 7 处裸 `ChatModel.call()` 后确认：它们的生命周期无法都塞进当轮 RoundTrace——
- **视觉识别**是独立请求（`/api/chat/attachment/process`，早于 send、早于 trace 建立，且请求本身不带 conversationId）；
- **记忆合并**是 afterReply 异步（trace 已落库）；
- 路由/参数抽取/查询改写在本轮前置链内（能拿 conversationId）。

故不做「硬塞 RoundTrace」，而是新增旁路表 `llm_usage`，5 处裸调用各记一条（purpose 维度区分），成本看板聚合 `llm_usage`（全量裸调用）+ `agent_trace`（回答本身）。

### 新增文件
- `entity/LlmUsage.java` + `mapper/LlmUsageMapper.java`（含 `@Select` 聚合方法 `aggregateDailyByPurpose`，返回 record `UsageAgg`）
- `trace/LlmUsageService.java`（旁路异步采集，复用 traceExecutor，`recordAsync` 双重载：完整版 + 自动取 model 便捷版）
- `service/CostService.java`（合并两路聚合 → CostSummary：按天对齐 answer/aux + 按用途归类；异常降级空视图）
- `controller/CostController.java`（`GET /api/cost/summary?days=`，默认 30、上限 90）
- `dto/CostSummary.java`（record：answerTokens/auxTokens/totalTokens/rounds + daily[] + byPurpose[]）

### 修改文件
- 5 处裸调用点注入 LlmUsageService 采集：`AgentRouter`（ROUTE，route 加 conversationId 重载）、`ParamFillingService`（CLARIFY，extractParams 穿透 conversationId）、`QueryRewriteService`（REWRITE）、`VisionService`（VISION，conversationId/traceId 都 null）、`MemoryMergeService`（MEMORY_MERGE，summarize 穿透 conversationId）
- `AgentRoundHandler`：两处 agentRouter.route 调用补传 conversationId
- `mapper/AgentTraceMapper.java`：加 `@Select` 聚合 `aggregateDailyAnswer`（返回 record AnswerAgg）
- `sql/schema.sql`（主建表段 + 末尾存量段各一份）+ `sql/alter.sql`：llm_usage 建表
- `static/chat.html`：顶栏 💰 成本按钮（不依赖 currentId）+ 成本弹窗（分段按钮切天数 + 两个图表容器）
- `static/js/app.js`：costModal state + openCost/closeCost/loadCost/fmtTokens + buildTrendOption/buildPurposeOption（复用 agent-dark 主题，close 时 dispose 图表实例）
- `static/css/style.css`：`.cost-summary`/`.cost-metric`/`.cost-seg`/`.cost-chart` 等样式
- `README.md`：特性 + API（成本看板）+ 数据库表（llm_usage）+ 前端界面四处同步

### 关键实现要点
- 聚合 SQL 用 `@Select` + `DATE_FORMAT(created_at,'%Y-%m-%d')` GROUP BY，项目此前无 `@Select` 先例（都是 BaseMapper selectList/selectCount），此处聚合最干净。
- `ChatResponseMetadata.getModel()` 可取实际模型名（便捷重载自动填充，避免 5 处重复解析）。
- 天数切换用**分段按钮**（3 个）而非原生 `<select>`——遵循项目「原生 select 弹层不可控」的既有结论，零弹层坑。
- 成本看板是观测、非业务：CostService 聚合异常降级空视图不抛错；LlmUsageService 全链路 try/catch 旁路。
