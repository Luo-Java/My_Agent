## 落地工具注册「动态接缝」（为接入 MCP 铺路）

**动机**：`ToolRegistry` 原只吃 `ToolProvider`（= 带 `@Tool` 方法的 Bean，靠 `MethodToolCallbackProvider` 反射解析）。而远端工具（MCP `tools/list`）**运行时才知道有哪些、schema 由对方给出，反射不出来**。

**改动（2 文件，零新依赖，向后兼容）**：
- 新增 `org.luo.tool.ToolCallbackSource`：`List<ToolCallback> toolCallbacks()` + `default String groupName()`。契约写明「在 `ToolRegistry` 构造期被调用，远端不可达须返回空列表并告警、**绝不能抛异常**，否则应用启动失败」。
- `ToolRegistry`：构造器追加 `ObjectProvider<ToolCallbackSource>`（用 `ObjectProvider` 保证**零实现时静默跳过**，不给启动加约束）；抽出私有 `register(group, callbacks, all, index, infos)`，两类来源共用「同名保留先注册者（注解式优先）+ 告警」逻辑；日志改为「N 个注解式 Bean + M 个动态来源」。

**验证**：离线 `run_mvn.sh` → `MVN_EXIT=0` / BUILD SUCCESS / **99 源文件**（98+1）。

**关键接线事实（供后续接入用）**：`ToolRegistry.resolve(toolsJson)` 是白名单唯一入口；`LenientToolCallbackResolver` 从 `ToolRegistry` 建索引做未知名兜底；`ChatComposer.decorateRequest` 是唯一挂载点（`spec.tools((Object[]) tools)`）。**故 MCP 工具必须进 `ToolRegistry`**，否则前端「工具装配」、白名单、兜底解析器三处都看不到。

## MCP 接入调研结论

- **离线仓库无任何 MCP 依赖**：`repository/org/springframework/ai` 下无 mcp 模块，也无 `io/modelcontextprotocol`。
- Spring AI **BOM 2.0.0 已管理** `org.springframework.ai:spring-ai-starter-mcp-client`（另有 `-webflux`、`spring-ai-mcp` 核心、`spring-ai-mcp-annotations`、`spring-ai-autoconfigure-mcp-client-{common,httpclient,webflux}`）→ **走官方路线必须先联网拉一次依赖**，否则破坏离线构建。
- 配置前缀：`spring.ai.mcp.client.{enabled,name,version,type,request-timeout}` + `stdio.connections.<名>.{command,args,env}` / `stdio.servers-configuration`（Claude Desktop JSON）/ `sse.connections.<名>.url`。
- **Windows 大坑**：`npx`/`npm`/`node` 是 `.cmd` 批处理，Java `ProcessBuilder` 不能直接执行 → 必须 `command: cmd.exe` + `args: ["/c","npx",...]`。
- **安全红线**：stdio = 本地拉起任意进程；server 配置只能来自自己的 yaml，**绝不能让用户/接口运行时新增 server**（等于任意命令执行）。MCP 返回文本视为不可信外部数据，只进工具结果位、不进 system 指令位。
- 自研路线可行且与项目既有先例一致（`RerankService` 因 Spring AI 无 rerank 抽象而手写 Hutool HTTP）；`LenientToolCallbackResolver.UnknownToolCallback` 已是「手写 `ToolCallback` record」的现成范式。自研关键点：stdio 单管道 → 请求/响应按 JSON-RPC `id` 配对 + 串行化。
