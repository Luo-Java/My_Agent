### P0 — agent_trace 的「RAG 引用 / 命中数」是死链（功能整体失效）
- **证据**：`RoundTrace.citations(List<KbCitation>)` 全项目**零调用**（grep `.citations(` 的命中全是 record 访问器，无一处是 RoundTrace 的写入方法）。
- **后果链**：`TraceService.persist` 第 75/76 行用 `trace.citationCount()` / `trace.getCitations()` 落 `agent_trace.kb_hit_count` / `citations_json` → **恒为 0 / NULL**。前端 `index.html:691` 的「📚 {{t.kbHitCount}}」永远显示 0；`index.html:717` 的「RAG 引用」块永远不渲染，落到 728 行兜底文案「无 RAG 命中」——与事实不符。
- **修法**：在 `ChatService` 拿到 `out.citations()` 后调 `trace.citations(out.citations())`。`chat()` 与 `doStream()` 各一处（或收在 `runRound` 返回处统一一处）。

### P1 — 同步接口 `/api/chat/send` 在回复为 null 时 NPE
- **证据**：`CallResponseSpec.content()` 在 Spring AI 2.0 源码中标注 `@Nullable`；`AgentRoundHandler:125` 直接 `spec.call().content()` 未判空 → `RoundResult.answer(null, ...)` → `ChatService.chat` 返回 null → `ChatController:82` `Map.of("content", reply)` —— **`Map.of` 拒绝 null 值 → NPE → 500**。
- **佐证**：`ChatService` 同文件里 `out.reply() != null ? ... : 0`、`emitChunks` 的 `if (full == null) full = ""` 都做了判空，说明作者也认为可能为 null。流式路径安全，仅同步接口中招。

### P2 — `RoundTraceAdvisor` 的 ThreadLocal 在 `before` 提前返回时不清理
- **证据**：`before()` 中 `if (trace == null) return request;` 未 `CURRENT.remove()`；`after()` 用 `response.context()` 优先、`CURRENT.get()` 兜底。
- **后果**：若某次调用在 `after` 之前抛异常（`after` 未执行），boundedElastic 复用的线程上会残留上一轮 trace；下一次该线程上「context 里无 trace」的调用会命中兜底分支，把 token **累加到上一轮已落库的 trace** 上，并让该 RoundTrace 被线程长期持有。
- **修法**：`before` 中 trace==null 时也 `CURRENT.remove()`。

### P2 — 规划模式把字面量 "null" 注入提示词
- **证据**：`PlannerRoundHandler.executeSteps`：`String userInput = (i == 0) ? firstInput : "上一步的输出：\n" + previous;`，`previous` 初值 null。若第 1 步失败/返回空（`previous` 未更新），第 2 步输入变成 `"上一步的输出：\nnull"`。

### P2 — 删除智能体不清 Chroma 专属库向量（孤儿残留）
- **证据**：`AgentService.deleteAgent` 只操作 MySQL（`chunkMapper`/`fileMapper`/`kbMapper`），**无** `chromaStore.deleteByChunkIds`；而 `KbService.deleteKb:199` 有。`syncToChroma` 是 upsert-only，不会清孤儿 → Chroma 里永久残留。
- 影响有限（检索按 kb_id 过滤，孤儿不会被召回），但存储持续累积。

### P2 — `SqlSafety.tableVerdict` 白名单可被逗号隐式 JOIN 绕过
- **证据**：`TABLE_PATTERN = \b(?:from|join)\s+...` 只抓 FROM/JOIN 后**第一个**标识符；`SELECT * FROM student, conversation` 只提取到 `student` → 通过白名单，但实际能读系统表。`validate_sql` 同样受影响。
- 另：MySQL 版本注释 `/*!50000 ... */` 会被 `stripCommentsAndStrings` 整段剥掉、却仍被 MySQL 执行 → 两层校验都可被绕过。

### P3 — `MemoryMergeService` 每轮全量 `getHistory`（无界）
- `maybeMergeMemory` 用 `getHistory`（全量 selectList），与已收敛的 `ParamFillingService`（`getRecentHistory(50)`）不一致；长会话每轮（异步）拉全量。且 `computeWindowStart` 在两处基于**不同长度**的列表计算——当预算覆盖超过 `DbChatMemory.SQL_FETCH_LIMIT=200` 条时，会产生「既不摘要也不注入」的空洞区。

### P3 — `chat_message.created_at` 是 `DATETIME(0)`，纳秒偏移被静默截断
- `DbChatMemory.add` 用 `base.plusNanos(1000)`、`saveClarifyExchange` 同样，意图保证同批顺序；但列是**秒级精度** → 同批两条 created_at 完全相同。`getHistory`/`getRecentHistory` 的 `ORDER BY created_at` **无 id tiebreaker**，目前靠 InnoDB 二级索引隐含主键的巧合才对，执行计划一变（filesort）就不保证。
- 修法：`ORDER BY created_at, id`；或列改 `DATETIME(3)`。

### P3 — 流式「打字机」延迟按分片累加
- `ChatService.stream` 的 `delayElements(15ms)` + 4 字/片 → 每 1000 字额外 3.75s；4000 字答案平白多等 ~15s。且它是**纯人为**延迟（内容早已生成完并缓冲）。

### P3 — `KbSearchService.refine` 单候选时跳过精排
- `if (sorted.size() > 1 && rerankService.available())` → 只有 1 条候选时落到兜底分支，阈值从 `rerank-min-score`(0.20) 静默变成 `min-score`(0.25)，与召回阶段的宽松下限 `recall-min-score`(0.10) 不一致 → 单条候选易被丢弃。

### P3 — `SqlQueryTool.failCounts` 无淘汰
- `ConcurrentHashMap` 按 SQL 文本累积，仅成功时移除；长期运行下失败过的不同 SQL 会持续驻留（增长有上界但无清理）。

## 第一批修复（P0/P1 接线类，4 项）

用户回「开始」= 执行第一批（#1+#2+#3+#4）。改动全是 1~2 行接线/判空，**无 DDL、无配置、无前端改动**。

### #1 修复 `agent_trace` 引用死链（P0，功能静默失效）
- **根因**：`RoundTrace.citations(...)` 全项目零调用 → `TraceService.persist` 的 `setCitationsJson`/`setKbHitCount` 恒为 NULL/0 → 前端追踪弹窗「📚 N」恒 0、引用块永不渲染、落到「无 RAG 命中」兜底文案（与事实相反）。
- **为什么 advisor 采集不到**：引用由检索环节（`ChatComposer.retrieve` → `KbSearchService`）产出，不在模型调用链上；`RoundTraceAdvisor` 只能看到工具调用与 token。
- **修法**：在 `ChatService.runRound` 的统一出口（fallback 兜底之后、`return r` 之前）接线 `if (trace != null && r != null) trace.citations(r.citations())`。
- **为什么放这里**：`runRound` 是同步/流式两个入口的唯一汇聚点，且已在 fallback 之后 → 拿到的一定是**最终生效**的 handler 产出的引用（规划回退时取 agent 路径那份）。

### #2 同步接口 null 回复 NPE（P1）
- `CallResponseSpec.content()` 标注 `@Nullable`；`AgentRoundHandler` 未判空 → `ChatController.send` 的 `Map.of("content", reply)` **拒绝 null 值** → NPE → 500。流式路径因 `emitChunks` 里有 `if (full == null) full = ""` 而免疫。
- **修法**：产生处 `AgentRoundHandler` 归一 `if (reply == null) reply = ""`（与流式一致）+ 出口 `ChatController` 再兜一道三目判空（廉价双保险）。

### #3 `RoundTraceAdvisor` ThreadLocal 泄漏（P2）
- `before()` 在 `trace == null` 时**直接 return**，没清 `CURRENT`。若上一次调用在 `after` 之前抛异常（`try/finally` 的 remove 不执行），boundedElastic 复用的线程会残留旧 trace → 下一次「无 trace」调用的 `after` 命中兜底分支 `CURRENT.get()` → **token 累加到已落库的旧 trace**。
- **修法**：无 trace 分支先 `CURRENT.remove()` 再 return。

### #4 规划步骤注入字面量 `"null"`（P2）
- `PlannerRoundHandler.executeSteps` 的 `previous` 初值 null，且只在步骤成功时更新 → 首步失败后第 2 步输入变成 `上一步的输出：\nnull`。
- **修法**：三分支——首步用原始目标；`previous == null` 时回落 `（上一步未产出可用结果，请基于原始目标作答）\n + firstInput`；否则用上一步输出。

## 第二批修复（一致性与校验类，4 项）

用户回「继续修复第二批」= #5~#8。**全程零 DDL**（唯一条目在 alter.sql 里是「说明项，无需执行」）。

### #5 删智能体不同步清 Chroma 向量（P2，静默残留）
- `AgentService.deleteAgent` 只删 MySQL 三表（kb_chunk / kb_file / kb），**完全没碰 Chroma**；而 `KbService.deleteKb` 有 `chromaStore.deleteByChunkIds`。`syncToChroma` 是 **upsert-only、不清孤儿** → 残留向量永久留在 collection，且 agent 删掉后再无任何入口能找回这批孤儿 chunk id。
- **修法**：注入 `ChromaVectorStoreService`（它只依赖 ChromaConnection，无循环）；**先取 chunkIds**（`select("id")`，与 `KbService.chunkIdsOfKb` 同款）→ 删 MySQL → `deleteByChunkIds`。**顺序不可换**：MySQL 行删掉后就再也查不到该清哪些向量。

### #6 SQL 表白名单两处绕过（P2，安全）
- **绕过 1**：旧 `TABLE_PATTERN` 只抓 FROM/JOIN 后**第一个**标识符 → `SELECT * FROM student, conversation` 只提取 `student` 即放行，逗号后的系统表照样能读。
- **绕过 2**：MySQL **版本注释**（`/*!…*/`）与**优化器提示**（`/*+…*/`）会被 `stripCommentsAndStrings` 整段剥离、却仍被服务端执行 → 「校验看到的文本」≠「数据库执行的文本」。
- **修法**：
  - `TABLE_CLAUSE_PATTERN` 改为抓「FROM/JOIN 之后的整段表引用」（懒惰匹配 + 三重终止：子句关键字 / `)` / 串尾），再按逗号切分、逐段取首标识符 → 同时解决「逗号多表」与「带别名」。
  - 新增 `containsExecutableComment()`：扫描（跳过字符串字面量）命中 `/*!` 或 `/*+` 即拒绝。**无法「还原后再校验」，只能拒绝**；正常查询不需要这两种注释。
- **实施中查出并修掉一个自己引入的漏洞**：初版终止符只有「子句关键字 / 串尾」，导致 **`FROM (SELECT * FROM conversation) t` 提取为空 → 系统表被静默放行**。补 `\)` 终止符后修复。用 Python 等价正则跑了 **15 个用例**（逗号多表 / 别名 / LEFT JOIN / 多级 JOIN / 子查询 / IN 子查询 / UNION / 反引号 / 大小写 / 换行 / CTE）全部符合预期。
- **有意保留的「过严」**：CTE 名会被当表名校验 → `WITH t AS (…) SELECT * FROM t` 被拒（旧实现也如此，不回归）。放行 CTE 名需先解析 WITH 定义，反而扩大放行面，故不做；已写进 javadoc。

### #7 记忆合并与注入的窗口口径不一致（P2，记忆静默丢失）
- **根因**：`MemoryMergeService` 在**全量** `getHistory` 上算窗口起点，`DbChatMemory.get()` 在**最近 200 条**上算同一函数 → 历史超过 200 条时两把尺子不同：摘要覆盖到 W、注入却从更靠后开始，中间那段**既不进摘要也不进上下文**（用户体感「模型莫名忘了前几轮」）。附带问题：每轮（异步）全量 selectList 随历史无界增长。
- **修法**：
  - `DbChatMemory.SQL_FETCH_LIMIT` 改 **public**（两处必须共用同一个值取**同一段列表**）。
  - `MemoryMergeService` 改用 `countMessages` + `getRecentHistory(SQL_FETCH_LIMIT)` + `computeWindowStart`，再**换算回全量索引**：`windowStart = total - recent.size() + startInRecent`。
  - 新增 `ConversationService.countMessages(cid)`（纯 count，不拉数据行）与 `getMessagesRange(cid, from, to)`（`LIMIT from, count` 只读待摘要的那一段）→ delta 不再依赖整段 history 常驻内存。
  - `getMessagesRange` 依赖「chat_message 不做物理删除」这一既有契约（否则索引区间会漂移），已写进 javadoc 与类注释呼应。

### #8 消息排序无 tiebreaker（P3，顺序靠巧合）
- `chat_message.created_at` 是 **DATETIME(0)**（秒级）：`DbChatMemory.add` 的 `plusNanos(nanoOffset)` 与 `saveClarifyExchange` 的 `plusNanos(1000)` **都会被静默截断**（schema 注释那句「相差纳秒级以保证顺序」是错的）。两处 `ORDER BY created_at` 无 id tiebreaker，当前正确只因 InnoDB 二级索引隐含主键，优化器一改走 filesort 就错序（表现为「用户的话与回答对不上」）。
- **修法（零 DDL）**：`getHistory`/`getRecentHistory`/`getMessagesRange` 三处统一 `(created_at, id)` tiebreaker；**删掉两处无效的纳秒偏移**（同批共用同一时间）；`schema.sql` 该列注释同步改为「顺序由自增 id 兜底」。**刻意不改列类型**：DATETIME(3) 仍需 tiebreaker（同毫秒多条），收益为零却要多一次 DDL，不划算。
- `alter.sql` 末尾追加「说明项（无需执行）」段落记录该决策，避免后人以为漏了 DDL。

## 第三批修复（体验 / 调优类，3 项）

用户回「修复第三批」= #9~#11。**零 DDL、零配置、零前端改动**，只动三个 Java 文件。

### #9 流式「打字机」延迟按分片线性累加（P3，体验，实际最痛）
- **根因**：`ChatService.stream()` 末端 `delayElements(15ms)` 对**每个** `token` 事件生效，而 `emitChunks`
  固定 4 字/片 ⇒ 人为延迟 = `字数/4 × 15ms`。4000 字答案平白多等 **~15 秒**，且这段延迟是**纯人为**的
  （内容早已由 `call()` 生成完并缓冲在内存里，用户只是在等动画播完）。
- **修法（帧间隔固定 + 分片自适应）**：帧间隔抽成常量 `TYPING_FRAME_MS=15`（`delayElements` 与切片共用，
  只此一处定义）；新增 `TYPING_MAX_MS=2000` 与 `TYPING_MIN_CHUNK=4`，`chunkSize(len) =
  len <= 帧数上限×4 ? 4 : ceil(len / 帧数上限)`（帧数上限 = `TYPING_MAX_MS/TYPING_FRAME_MS` = 133）。
  于是「帧数 × 帧间隔 ≤ 2000ms」——**总时长恒定有界**。短答案（≤532 字）仍是 4 字一片的逐字观感。
- **自检数据**（Python 等价实现）：100 字→0.38s；532 字→2.00s；1000 字→1.88s；4000 字→1.95s；20000 字→2.00s。
- **为什么不是「调小 delayElements」**：那样短答案的打字观感一并丢失，且仍是线性；分片自适应才是同时保住观感与上界。

### #10 精排阈值口径随候选条数静默变化（P3，与既有设计相悖）
- **根因**：`KbSearchService.refine` 的入口判断写的是 `sorted.size() > 1 && rerankService.available()`，
  于是「只有 1 条候选」会落到兜底分支，阈值从 `rerank-min-score`(0.20) **静默变成** `min-score`(0.25)
  ——与召回阶段的宽松下限 `recall-min-score`(0.10) 也不一致，单条候选因此常被丢弃。
- **修法**：改为 `!sorted.isEmpty() && rerankService.available()`。理由：精排是 query↔**单条**文档
  **独立**打分（不是文档之间两两比），与候选条数无关，1 条候选调用精排同样有意义，不该被跳过。
  「候选数为 1 时还要不要多花一次 HTTP」曾是原 guard 的动机，但与「阈值忽高忽低」的正确性问题相比不划算。
- 兜底分支（精排**真不可用**时）仍用 `min-score`(0.25) —— 这是**有意**的：没有精排分时就只能用向量分尺子，
  属「精排上线前的原始行为」，与本次修的「有精排却按条数走错分支」是两回事。

### #11 `SqlQueryTool.failCounts` 无淘汰（P3，长期运行占用）
- **根因**：`ConcurrentHashMap` 按规范化 SQL 累积失败次数，原先只有两个清理时机——「同一条 SQL 执行成功」
  与「全局熔断」。模型每改写一次 SQL 就产生**新 key** ⇒ 失败过的不同 SQL 长期驻留（增长有上界但永不回收）。
- **修法**：新增 `MAX_TRACKED_SQL=500` 与插入序队列 `failKeys`（`ConcurrentLinkedDeque`）；
  首次失败时 `putIfAbsent` 返回 null 才 `addLast`（登记顺序），失败后调 `evictOldestFailureCounts(key)`
  按 FIFO 淘汰最早记录并同步 `failCounts.remove`；熔断时两个结构一起 clear。
- **一个刻意的简化**：成功时**不**回删 `failKeys`（`ConcurrentLinkedDeque.remove` 是 O(n)）。
  队列自身按容量自限，残留 key 在淘汰时对 map 做一次**幂等** remove 即可 ——
  由此 `failCounts` 的键集恒为 `failKeys` 的子集，**两张结构都有上界**。已在字段 javadoc 写明该不变量。
- 并发防御：`get` 为 null 时用 `computeIfAbsent`（lambda 无副作用，避免 `computeIfAbsent` 重试导致重复入队），
  同时规避「拿到计数后才发现是 null」的 NPE。
