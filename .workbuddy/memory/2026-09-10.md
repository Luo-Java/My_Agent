## 技术调研：Spring AI 2.0 原生多模态可用性（回答用户「识别图片只能通过 HTTP 接口吗」）

**结论：不是只能 HTTP。** 当前 `VisionService` 用 Hutool `HttpUtil` 手拼 JSON 直连 dashscope `/chat/completions`，属于**绕开框架的手写实现**；Spring AI 2.0 原生支持多模态，且项目里已有 4 处「裸 ChatModel 直调」先例，改用原生反而更统一。

### 反编译验证的 API 清单（spring-ai-* 2.0.0，均确认存在）

| 类 | 坐标 | 关键签名 |
|---|---|---|
| `Media` | `org.springframework.ai.content.Media`（**在 spring-ai-commons，不在 spring-ai-model**） | `Media(MimeType, Resource)` / `Media(MimeType, URI)` / `Media.builder().mimeType(..).data(Resource).build()` |
| `UserMessage` | `org.springframework.ai.chat.messages.UserMessage`（spring-ai-model） | `UserMessage.builder().text(String).media(Media...).build()`；实现 `MediaContent`，有 `getMedia()` |
| `Prompt` | `org.springframework.ai.chat.prompt.Prompt`（spring-ai-model） | `Prompt(List<Message>, ChatOptions)` |
| `OpenAiChatOptions` | `org.springframework.ai.openai.OpenAiChatOptions` | `builder().model("qwen-vl-plus").temperature(0.2).build()`；**`model(String)` 由父类 `DefaultChatOptionsBuilder` 提供**，支持 per-request 覆盖模型 |
| `ChatModel` | `org.springframework.ai.chat.model.ChatModel` | `ChatResponse call(Prompt)`（另有 `call(String)`/`call(Message...)`） |
| `ChatResponse` | 同上 | `getResult()` → `Generation.getOutput()` → `AssistantMessage.getText()`（getText 来自 `AbstractMessage`） |

### 原生写法（约 10 行，替代当前 ~80 行手写 JSON/HTTP）

```java
UserMessage msg = UserMessage.builder()
        .text(props.prompt())
        .media(new Media(MediaType.parseMediaType(mime), new ByteArrayResource(bytes)))
        .build();
Prompt prompt = new Prompt(List.of(msg),
        OpenAiChatOptions.builder().model(props.model()).temperature(0.2).build());
ChatResponse resp = chatModel.call(prompt);          // 裸 ChatModel，不走 advisor
String caption = resp.getResult().getOutput().getText();
```

### 关键判断依据

- **裸 ChatModel 直调是本项目既有模式**：`AgentRouter` / `MemoryMergeService` / `ParamFillingService` / `PromptService` 均注入 `ChatModel` 直接 `call()`（绕开 advisor 与记忆），所以 vision 用同一模式不算引入新范式，反而消除「全项目唯一手写 LLM HTTP 调用」这个孤例。
- **原生顺带解决多图串行问题**：`media(m1, m2, ...)` 可变参 → 一次调用传多图；当前 `describeAll` 是 for 循环 N 次 HTTP 串行。
- **per-request 换模型安全**：`OpenAiChatOptions.builder().model("qwen-vl-plus")` 只影响本次 Prompt，不动 yaml 里主对话的 qwen3.7-plus。
- **唯一待实测风险**：dashscope OpenAI 兼容端点对 Spring AI 生成的 `image_url`（base64 data URI）结构是否完全兼容——按约定不启动项目，需用户 IDE 重启后实测；若失败可回退现有 Hutool 实现。

#### 关键决策

1. **保持 `describeAll` 1:1 契约不变** —— 前端 `a.caption = captions[pi]` 逐图对齐消费，所以**没有**改成「一次调用传多图、返回一段合并描述」（那会破坏 per-image caption 展示）。原生 `media()` 可变参能力保留待用。
2. **多图改并发**（原为 for 循环串行 HTTP）—— `CompletableFuture.supplyAsync(.., visionExecutor)` 提交、按入参顺序 `future.get()` 回收，延迟从 N×t 降到 ≈t；提交期被拒（线程池满）降级占位 caption，不抛错。
3. **`timeoutSeconds` 语义保留** —— Spring AI 无 per-request 超时，改在编排层用 `future.get(timeout, SECONDS)` 实现；超时 `cancel(true)` + 占位文本，底层 HTTP 调用由全局客户端超时兜底。
4. **失败降级不变** —— 单图失败/超时/过大/非图片一律占位 caption，绝不影响其它图、不抛错给调用方。

## 决策：多图识别保持「逐图并发」，不改成「一次请求传多图」

**用户追问**：「ai 不支持一次识别多个图片吗」——质疑为什么用了异步线程池而不是单次调用。

**结论：技术上都支持，但选定保持逐图并发。**

- Spring AI `UserMessage.media(Media...)` 是可变参、dashscope 视觉模型接受 content 数组多图，**一次请求传 N 张图技术上可行**；
- **但一次请求 = 一段合并文本**，会丢失「哪段描述来自哪张图」的归属。

**决定性依据（看下游消费方式）**：`ChatController.composeWithAttachments` 按
`图片N（filename）：caption` **逐条带文件名标注**注入上下文。若合并成一段，LLM 就无法区分
「工资条」与「聊天记录」各自内容——对劳动仲裁场景是实打实的信息损失。

**逐图并发的其它收益**：单图失败隔离（一张出错只降级该图）、单图识别质量更高（模型不分散注意力）、
延迟由并发压平（N×t → ≈t）；**token 成本与一次调用基本相当**（每张图同样只传输一次，仅 80 字指令重复 N 遍）。

**已知唯一劣势**：跨图联合对比（模型同时看到多图才能判别的细微差异）弱于单次调用。
若未来要做「对比这两张图」，才应改为合并调用。

**落地**：把上述决策理由写入 `VisionService` 类 javadoc「为什么不是一次请求传多图」段落
（沿用 ParamFillingService/MemoryMergeService 的双向契约注释风格，防止后人顺手"优化"掉）。

**验证**：独立诊断程序两个场景全绿 —— ① 集合已存在 → 初始化 OK；② 全新集合（模拟新装 Chroma）→

## Chroma 检索「查不到数据」根因（第三次修复，最关键）

**现象**：`chromaStore.search(...)` 永远返回空，RAG 一直回退 MySQL。但 status 显示 connected=true、documentCount 27、space=cosine，数据确实在。

**真因：Chroma 0.5 的 cosine 距离语义与 Spring AI 假设不符**。实测对同一条 chunk：
- 用 DashScope `qwen3.7-text-embedding` 在外面算的真实余弦 = **0.588**
- Chroma 返回的 `score` = **0.176**，且 `0.176 ≈ 2×0.588 − 1` 在所有样本上完美吻合

即 **`distance = 2·(1 − cosine_sim)`（归一化向量平方欧氏距离），Spring AI 把 `score = 1 − distance = 2·cosine_sim − 1`**。
项目之前的 `search()` 和 Spring AI 的 `similarityThreshold` 都把 Chroma 的 score 当真实余弦、再套 `MIN_SCORE=0.25` 过滤
→ 真实余弦 0.5~0.6 的相关结果被压扁成 0.0~0.2 全被滤掉。**不是连接问题、不是 metadata/OR 问题、不是维度问题、不是模型不一致**（库向量已验证是 qwen3.7 写的，余弦 0.977）。

**修复（`ChromaVectorStoreService.search`）**：
1. `similarityThreshold(-1.0)` 关闭 Spring AI 客户端过滤（避免被压扁的分数二次过滤丢候选）
2. 循环里 `realCos = (rawScore + 1) / 2` 还原真实余弦，再 `if (realCos < minScore) continue`
3. 抽 `toRealCosine()` 静态方法；删掉旧的 `toSpaceThreshold()`（l2 分支不再需要，集合统一 cosine）

**验证**：同样本 `raw=0.1767 → realCos=0.588 ≥ 0.25` 保留，与 MySQL 余弦检索同尺度。BUILD SUCCESS。
**排查手法升级**：用 python 既可直接读 `chroma-data/chroma.sqlite3`，也可用 DashScope `/compatible-mode/v1/embeddings` 实时向量化 query，对照 Chroma HTTP `query` 接口返回的 score，是定位「score 语义/空间/模型不一致」的杀手锏。
**配置提醒**：`spring.ai.openai.embedding.model` 实际是 `qwen3.7-text-embedding`（注释写的 `text-embedding-v3` 已过时），注释需同步。

## Chroma 检索再修：绕过 Spring AI similaritySearch 的阈值陷阱（用户报 "Similarity threshold must be in [0,1] range"）

**根因**：上次把 Chroma 的 cosine 距离换算成真实余弦后，为关掉 Spring AI 客户端阈值过滤传了 `similarityThreshold(-1.0)`，但 `SearchRequest.Builder` 校验 `threshold ∈ [0,1]`（源码 `Assert.isTrue(threshold >= 0 && threshold <= 1, ...)`）→ 直接抛异常「Similarity threshold must be in [0,1] range」。更深的隐患：即便传 `0.0`（ACCEPT_ALL），ChromaVectorStore 的过滤 `if ((1 - distance) >= threshold)` 只留 `cos ≥ 0.5`，会把 [0.25,0.5) 的弱相关命中在到达我自己的 `toRealCosine` 过滤前就丢光。

**修法（ChromaVectorStoreService）**：`search()` 不再走 `s.similaritySearch(SearchRequest)`，改为直接 `api.queryCollection(tenant, database, collectionId, QueryRequest)`，内部自己 `embedding.embed(query)` 向量化（query 只算一次，多库合并用 `where.$or` 一次查完）；`store()` 成功时一并持有 `api/embedding/collectionId` 三字段。解析 QueryResponse 后按 `realCos = 1 - distance/2`（= toRealCosine(1-distance)，cosine/l2 归一化向量均可）与 `MIN_SCORE` 比较过滤，查不到/异常才回退 MySQL。删 `SearchRequest` import。BUILD SUCCESS。

**验证**：python 复现新链路——真实中文问题 `embed` + 原生 query（kb_id=1 单库 / `$or`≥2 多库）均返回命中，realCos 0.54~0.70 全 ≥ 0.25；2 元素 `$or` 被 Chroma 接受。

## 重构：抽出 ChromaClient（检索样板收口，等同 LangChain similarity_search 一行调用）

**动机**：`ChromaVectorStoreService` 把连接/降级/写入/检索全混在一起（检索相关的 `search`/`buildWhere`/`parseHits`/`toRealCosine`/`parseId`/`ChromaHit` 占了大段样板）。用户对比 LangChain `similarity_search` 的简洁，要求把脏活收进独立客户端。

**改动**：

## 重构#3：抽出 ChromaConnection，门面彻底瘦身为纯业务层

**动机**：`ChromaVectorStoreService` 在重构#2 后已是「连接门面」，但还混着连接生命周期（ensureConnected/connected/markFailed/logSkipped）+ collection 引导全套原生 HTTP helper（~150 行），与「业务门面」语义仍交叉。用户追问「connected 也能抽吗、放这合适吗」，结论：`connected` 单独抽会割裂生命周期单元，正确对称做法是把**整个连接生命周期**连同它一起挪到新 `ChromaConnection`，让门面只剩「实体转换 + 编排 + 降级日志」。

**改动**：
- 新建 `ChromaConnection`（@Service，同包）：持有全部连接配置与生命周期状态——`@Value` baseUrl/collectionName/tenant/database/retryIntervalSeconds/upsertBatchSize、`ObjectProvider<EmbeddingModel> embeddingProvider`、volatile 字段 chromaClient/nextRetryAt/lastError/space/lastSkipLogAt、`SKIP_LOG_INTERVAL`；迁入 `ensureConnected`(DCL+冷却重试) / `connected(op)`(取客户端或降级) / `markFailed` / `logSkipped` / `status()` + `ensureCollection` 全套原生 HTTP helper（`createCollectionNative`/`postCollection`/`hnswConfig`/`deleteCollectionNative`/`detectSpace`/`countQuietly`/`collectionsUrl`/`trimSlash`/`chop`）。`connected` 与 `status` 为 public（供门面调用），其余 private。
- `ChromaVectorStoreService`（@Service）改为**纯业务门面**：构造器注入 `ChromaConnection`；`upsertChunks`/`deleteByChunkIds`/`search` 改为 `connection.connected(op)` 取客户端 + `KnowledgeChunk→ChromaDoc` 转换 + 委托 `ChromaClient`；`status()` 直接 `return connection.status()`；移除全部连接/collection helper 与连接内参泄漏（日志删掉「每批=N」，批大小本就是 ChromaClient 内部职责）；类 javadoc 重写为「业务门面」定位。
- 三层分层定型：① `ChromaConnection`=连接生命周期；② `ChromaClient`=Chroma 全量操作适配；③ `ChromaVectorStoreService`=业务门面（翻译+编排+降级）。对外契约零变化，`KbService`/`KbSearchService`/`KnowledgeBaseController` 完全不用改。

**行为不变**：lazy+冷却重试、命名空间/cosine 空间校正、双写降级 warn+回退 MySQL、余弦还原与多库 `$or`、状态接口全部保持。
