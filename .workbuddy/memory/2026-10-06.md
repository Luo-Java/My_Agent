## 实现：智能体转交（call_agent）+ 规划「先看计划」
用户从扩展方向清单里挑了 4 + 3，已落地并 `mvn package` 通过（无新增 javac 告警，只剩 Maven 自身的 `compilerVersion` 参数废弃提示）。

**方向 4 · Agent-as-Tool（`call_agent`）**
- 新增 `org.luo.ai.tool.SubAgentTool`：**每轮现构** `ToolCallback`（自实现，`DefaultToolDefinition.builder()` 造 name/description/inputSchema；Spring AI 2.0 的 `ToolCallback.getToolMetadata()` 有默认实现，只需实现 `getToolDefinition()` + `call(String)`）。
- **不能走 `ToolProvider` 注解式**：`@Tool` 方法集在编译期固定、`ToolRegistry` 只构造期快照一次，而 agent 是运行时数据。也不能走 `ToolCallbackSource`（同样构造期一次性）。故由 `ChatComposer.decorateRequest` 每轮合并注入。
- `ToolRegistry` 新增**第三类「动态工具」**：只登记 `ToolInfo` 进 `availableTools`（供前端勾选），不入 `byName`；`resolve()` 命中 `DYNAMIC_TOOL_NAMES` 时**静默跳过不告警**；新增 `dynamicToolRequested(toolsJson, name)`。
- **白名单专属**：`tools_json` 为 `NULL`（全量）时**不挂** —— 转交是策略性能力，默认下发给所有智能体会让翻译/闲聊类误用，且一次性改变存量行为。
- **只做一层，天然无环**：子智能体挂的是它自己的静态工具（不含 `call_agent`），故不存在 A→B→C 递归/调用环，**不需要 ThreadLocal 调用链与深度配置**。
- **破环关键**：`SubAgentTool` 注入 `AgentMapper` 而**不是** `AgentService` —— 因为 `AgentService → PlannerService → ChatComposer → SubAgentTool` 会成构造器环（与 AgentService 级联清知识库时「直接操作数据层避免循环依赖」同一处理）。
- 成本按 `SUBAGENT` 记入 `llm_usage`（`CostService.PURPOSE_LABELS` / `LlmUsage` 注释 / 两处 SQL 注释同步）。
- 前端：工具分组 label 加 `SubAgent` → 「智能体协作」。

### 实测确认的硬伤（带证据）
- **SQL 表白名单可被块注释绕过（最严重，已用真实类复现）**：`SqlSafety.tableVerdict` 把**原始 SQL** 交给 `extractTables`，而 `TABLE_CLAUSE_PATTERN`（`SqlSafety.java:45-47`）要求 `from|join` 后跟 `\s+`；`FROM/**/` 中间无空白 ⇒ 提取不到表名 ⇒ `tables.isEmpty()` 走 `:86-88` 放行。实测（`java -cp target/classes` 直接调该类）：`SELECT * FROM/**/sys_user`、`SELECT content FROM/**/chat_message` 两条 **tableVerdict 均返回 null（放行）**，而 `SELECT * FROM sys_user` 被正确拦下。MySQL 视 `/**/` 为 token 分隔符 ⇒ 实际执行 `FROM sys_user`。叠加数据源默认 `root`（`application.yaml:30`）⇒ **任意登录用户可读 `sys_user.password`（BCrypt 哈希）与其他用户全部 `chat_message`**。修法：表名提取建立在 `stripCommentsAndStrings` 之后的文本上（注意该函数**不留空格**，`FROM/**/x` 会变成 `FROMx`，故还应顺带补一个空格）；或换 JSqlParser（项目已有 `mybatis-plus-jsqlparser`）；并给 SQL 工具单独配只读账号。
- **edu 模块零鉴权**：`grep -rn RequireRole src/main/java/org/luo/edu/` **空**；全项目 5 处 `@RequireRole` 全在 system/ai。任何登录用户可增删改查全部学生/成绩/教师，且无归属概念（IDOR 天然存在）。同性质的还有 `/api/agent`、`/api/kb` 写接口（可删全局知识库）。
- **JWT 密钥硬编码进仓库**：`application.yaml:141` 默认值是固定 64 位 hex，随源码分发；README §3.1 声称"密钥不进仓库"与事实不符。任何人可伪造 ADMIN token。
- **初始管理员 `admin` / `admin123`**：`application.yaml:146`。
- **DDL 不一致**：`kb_file.chunk_strategy` / `chunk_overlap` 只在 `schema.sql:88-89`，`alter.sql` **无任何 `kb_file` 语句** ⇒ 存量库执行 alter 后缺列报 `Unknown column`。（这条直接踩用户红线「schema 与 alter 必须同步」。）

**12 · 局部重规划（P3-13）**
- 语义：只重排「**第一个未成功步骤及其之后**」的一段，已完成步骤与其产出保持不动。与续跑的分工：续跑 = 原计划再跑一遍；重规划 = 这一段本身行不通、换一套。改完**不自动执行**（与「先看计划」同一节奏，保持「先看 / 再改 / 后跑」一致）。
- 链路：`POST /api/chat/task/replan`（同步，一次模型往返）→ `ChatService.replan` → `PlannerRoundHandler.replanTask` → `PlannerService.replan`（新提示词 `prompts.yaml` 的 `planner-replan-system`，含 `{agentList}`）。
- **关键设计：上游产出不外传**。重规划段内第 1 层是「无依赖」步，执行时输入 = 原始目标（`firstInput`），**拿不到上游产出的原文**；所以提示词要求模型把上游结论**内联进 instruction**。这样新步骤的 `dependsOn` 只需「段内相对下标」，不需要跨段依赖，实现大幅简化。
- **最要命的一处：`step_index` 必须连续**。续跑重建依赖映射用的是**列表位置**而非 step_index（`resumeTask` 里的 `remap[i]`），若保留段留下下标空洞（如 0,1,3），依赖里写的 3 会超界被**静默过滤成「无依赖」**、执行语义悄悄改变。故 `TaskService.replanTail` 把保留段压紧到 `0..k-1` 并重映射它们各自的 depends_on。`task_step` 没有 (task_id, step_index) 唯一约束，所以「先改下标、后删旧行」的中间态不会冲突。
- 上游摘要每步截 500 字符（`REPLAN_SUMMARY_CHARS`），防「已完成步骤数 × 产出长度」无界拼进一次规划请求。

### C2 · 步骤审批点（「跑一半停下来问你」）
- **审批关卡独立于 `status` 状态机**（`task_step.approval_required` / `approved` 两列，DDL 同步 schema.sql + alter.sql）。理由：若把「待审批」做成一个 `status` 值，`markStepRunning`、`isSettled`、续跑重试判定等**所有既有分支**都要额外为它加一个态；两列正交后，执行侧只需在「找 ready 步骤」处插一道闸门。status 说「跑到哪了」，审批说「允不允许跑」。
- **闸门粒度 = 整条流水线暂停**（不是只挡该步、兄弟步照跑）。后者会让用户看到「卡住那步后面的步骤先出了结果」，流水线因果顺序难解释；「到此为止」才符合审批点的直觉。`ready` 按下标升序 ⇒ 取到最靠前那步。
- **又是「一次落库 + 现成通路」**（本项目**第 5 次**复用，前四次 = 先看计划 / 断点续跑 / 局部重规划 / 模板套用）：批准后走的就是 `POST /api/chat/task/resume`，`ChatController` 的 `POST /api/chat/task/approve` **只落标记不触发执行**；终止走 `POST /api/chat/task/cancel` 置 `CANCELLED`。
- **specs 下标 ≠ step_index**：续跑时被删掉的 agent 会被跳过（specs 变短），而审批/编辑接口按 `step_index` 落库 ⇒ 单列 `specStepIndex` 做换算，避免「显示第 3 步、实际改到第 4 步」。`ApprovalGate` 用 `boolean[]` + `of(...)` 构造，**全步骤都无需审批时返回 `null`**，让执行循环零判断（不引入恒假分支）。
- **取消审批要清 `approved`**：否则「先勾→批准→取消→再勾」会沿用旧批准，用户以为重新设了关卡、实际已被静默放行。这条写在 `TaskService.updatePendingStep` 里。

## 第十二轮 · 第三批功能扩展 3 条（C1 并行评审 + A3 跨会话搜索 + D2 内容安全）

范围由用户在 6 项候选里点选：**C1 + A3 + D2**。三项都追「能力维度」的拓展，且都复用现成通路（本轮第 6、7 次复用「一次落库 + 现成通路」接缝）。

### 三条能力的设计取舍
- **C1 并行评审为什么与规划互斥**：两者都是**编排形态**（规划决定「怎么拆」、评审决定「谁来答」），同时开着会让「本轮走哪条链路」取决于读取顺序。处理方式是「开启任一方**顺手关掉另一方**」而不是报错 —— 用户拨开关的意图明确，替他做掉这一步比让他来回点两次更合理。落在 `updateReviewEnabled`（开评审置 `planner=false`）与 `updatePlannerSwitch`（开规划置 `reviewEnabled=false`），`selectHandler` 里再留一道同序防御（规划 > 评审 > 普通）。
- **候选由 LLM 选、不是固定名单**：固定名单会让「问数学题也拉翻译官进来」。会话已显式绑定智能体时它**固定占一席**（用户选了它就说明要它参与），其余按问题类型补足；库里不足 2 个智能体直接返回空、**不调模型**（一个候选构不成「评审」）。
- **候选互不可见 + 共用同一份 kb/recall**：互相可见会退化成串行接力（后答者跟着前面的思路走）；素材各取一次既控成本（否则 N 份 RAG + N 次召回），也保证「谁答得好」里不会混进「谁拿到的资料多」。
- **A3 为什么是关键词而不是向量**：会话消息逐轮写入 ⇒ 走向量检索意味着每条消息落库要多一次 embedding + 新增一套副本维护链路 + 与 `kb_chunk` 共用空间互相干扰。代价是**换个说法就召回不到**（字面匹配），这是明确接受的边界，写进了 `CrossSessionProperties` Javadoc 与 README。
- **D2 与「在提示词里写一句安全要求」的本质区别**：后者把「守不守法」交给模型自己判断，拦不住明确不该出现的内容，也拿不到可观测的拦截记录。护栏是代码里的**确定性判断**（正则）。**如实标注两条边界**：字面正则不是语义审核（换说法/谐音可绕过）；输出侧替换**只作用于推送与展示**，库里仍是模型原始输出（普通对话的消息由记忆 Advisor 在模型返回时即落库，要让落库也替换得把护栏下沉进 Advisor 改写 response，会牵动 token / 工具元数据重建 —— 本版本刻意不做）。

### 三处「不许静默」的落地
- **输入命中**：`ChatController` 在**配额之前**拦（超限/命中 → 422 `CONTENT_BLOCKED`），**零模型调用**。

## 第十三轮 · 链路追踪弹窗「数据一多就变形」修复 + 分页（2026-10-06）

用户报障：截图显示追踪弹窗列表行的文字被压扁、上下重叠，越往下越明显。诉求是「做成分页」。

### 根因（不是数据问题，是布局问题）
`.trace-list` 是 `display:flex; flex-direction:column; max-height:52vh; overflow-y:auto`，而 `.trace-item` 没设 `flex` ⇒ 默认 `flex-shrink:1`。内容总高超过容器时，flex **等比压扁每个子项** —— 而且是压到**刚好贴合容器**，于是既不溢出、也不出现滚动条，表现就是行高塌陷 + 文字被各自的 `overflow:hidden` 裁掉后重叠。

修法一行：`.trace-list > * { flex: 0 0 auto; }`。同时 `.trace-list` 补 `flex:1 1 auto; min-height:0`，让「容器不够」正常转化为内部滚动。

### 为什么要三处一起改（不只是加个页码条）
用户诉求是分页，但**分页只降低触发概率、不治根**（10 条也可能撑爆矮窗口），所以两件事都做：
1. **CSS 治根**：任何条数都不塌陷；
2. **分页**：`TRACE_PAGE_SIZE=10`，数据量只影响页数、不影响行高。

分页带来的三个连带口径（都容易漏）：
- **统计条继续基于全量 `items`** —— 它回答「这个范围的总体情况」（轮次 / token 合计 / 平均耗时），不是「这一页」。若改成按页算，含义会静默变掉。
- **展开态 key 从列表下标改为 `traceId`** —— 用下标时「第 1 页第 3 条」和「第 2 页第 3 条」共用一个 key，翻页会串。这是分页**必然会**引入的 bug，不是顺手改。
- **`openTrace` 里 `page=1` 重置** —— 切范围 / 刷新后若停在旧页码上，可能停在一个已不存在的页。

### 反证（证明根因，而不只是「改完就好了」）
`probe_trace_collapse.js` 在同一页面上三步递进（`PREVIEW_TRACE_BULK=60` 起服务）：

| 步骤 | itemH | rowH | 行间距 |
|---|---|---|---|
| ① 现状（已修 CSS + 分页 10 条） | 36~36 | 34 | **42** |
| ② 仅把容器收到 120px（flex 已修） | 36~36 | 34 | **42** |
| ③ 再把旧 flex 注回（`flex:1 1 auto !important`） | **2~2** | 34 | **8 ← 行重叠** |

②证明「容器小」本身不会压扁子项（正常滚动），③证明注回 `flex-shrink` 立刻复现重叠 ⇒ 根因确认为 flex-shrink，而非容器高度或数据量。

**⚠ 取证方法论（踩了一次）**：第一版探针量的是 `.trace-row` 的高度，三步都返回 34，**看起来像「注回旧 flex 也没塌」**。实际是量错了对象 —— `.trace-row` 的高度由自身盒模型决定，父项被压扁时它只是被 `overflow:hidden` 裁掉，自身 `getBoundingClientRect().height` 不变。**正确指标：`.trace-item` 高度（36 → 2）+ 相邻行 `top` 之差（42 → 8）**。

### 顺带修掉一个工具缺陷（本轮阻塞过验证）
`serve_preview.py` 原本是 `socketserver.TCPServer`（**单线程**）。Chrome 并发拉 `app.js` / vue / css 等 6 个资源时被串行阻塞，偶发某个脚本加载失败 ⇒ **页面 DOM 完整但 Vue 根本没挂载**（`mustache` 残留 234、`errs=[]`）。第一轮探针的 `mustache残留=234` 就是这个，当时差点误判成「我把 chat.html 的模板改坏了」。查证方式：逐个 `curl` 静态资源**全是 200**，但页面仍不挂载 ⇒ 问题在服务并发能力，不在自己的代码。已换 `ThreadingTCPServer` + `daemon_threads=True`，改完 `mustache=0` 稳定。

另一条探针写法教训：`?__auto=send` 建会话是异步的（内部 `await fetch`），而 `--virtual-time-budget` 会把 `setTimeout` 瞬间跳过 ⇒ 固定 `setTimeout(2400)` 采数时 `currentId` 还没设好、顶栏「追踪」按钮不存在，探针报 `tracePillFound=false`（看着像功能没做）。改为 `waitFor(fn, tries)` 轮询（`await sleep(50)` 直到元素出现）后正常。
