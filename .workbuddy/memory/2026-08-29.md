# 2026-08-29 开发日志

## 新增：执行过程实时展示（progress 事件），过程不进记忆（11:20）
- 需求：运行时在对话里展示执行过程/步骤，但**过程不写会话记忆，只有最终结果写记忆**。
- 协议设计：新增 `org.luo.dto.StreamEvent(type, text)`，两种类型：
  - `token` —— 正文分片，累加进消息气泡，**唯一进记忆**的内容；
  - `progress` —— 执行过程，仅运行期展示，**绝不进记忆**（刷新/重开会话即消失）。
  - SSE data 的 JSON 字段名直接用事件类型：`{"token":"..."}` / `{"progress":"..."}`，`token` 字段与旧前端兼容。
- `ChatService` 改造：
  - `stream()` 返回 `Flux<StreamEvent>`，实现改为 `Flux.create(...)` + `subscribeOn(Schedulers.boundedElastic())` + `delayElements(15ms)`；执行体抽到 `doStream(conversationId, message, FluxSink)`。
  - **关键**：必须 `subscribeOn(boundedElastic)`，否则 `Flux.create` 在 Tomcat 请求线程同步跑完，SseEmitter 会把 send 攒进 earlySendAttempts 最后一次性 flush，进度就失去"实时"意义。
  - `streamChunks(...)` 改为 `emitChunks(sink, full, ...)`（推 token 事件 + touch + maybeMergeMemory）；追问文本改为 `sink.next(StreamEvent.token(...))`。
  - `handlePlannerConversation(..., Consumer<String> progress)` 与 `executeSteps(..., Consumer<String> progress)` 加进度回调；同步 `chat()` 传常量 `NO_PROGRESS`（空实现，进度仅流式支持）。
  - 播报点：规划中 → 计划清单（含每步 agent 名与 instruction）→ 每步 `▶ 执行中` / `✔ 完成（产出 N 字）` / `⚠️ 未产出` / `✖ 失败` → `✅ 全部完毕`；回退路径也播报。
  - 普通（非 planner）对话顺带播报 `🤖 已交由智能体「X」处理`（agent==null 的闲聊不播报，不打扰）。
  - 记忆写入逻辑未变：仍由 `savePlannerExchange` 只写「用户原话 → 最终回复」。
- `ChatController.stream`：`Flux<StreamEvent>` → `emitter.send(Map.of(event.type(), event.text()))`，text 为 null 兜底空串。
- 前端：
  - `app.js`：assistant 消息对象加 `steps: []` + `stepsOpen: true`；`flushEvents` 先判 `parsed.progress` 推入 `m.steps`，否则按 `parsed.token` 累加正文；**正文首个分片到达时自动收起过程区**（`if (!m.content && m.steps.length) m.stepsOpen = false`）。
  - `index.html`：AI 气泡内正文之前加 `.steps-box` 折叠区（标题「执行过程 · N 条」+ 右侧「不计入会话记忆」提示），`v-if="m.steps && m.steps.length"` —— 历史消息无该字段故天然不显示。
  - `style.css`：新增 `.steps-box/.steps-head/.steps-caret/.steps-hint/.steps-body/.steps-line`，虚线边框弱化，最后一条进度高亮（`:last-child` 用 `--text`）表示"当前在做什么"。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务** + 前端 Ctrl+F5。
- 设计要点复盘：「过程 vs 结果」的隔离靠**两条通道**而不是靠文本标记——事件类型决定渲染目标，记忆写入始终只认最终结果，二者不会互相污染。

## 优化：先返回数据，再处理记忆（11:35）
- 问题：`emitChunks` 里在推 token **之前**调 `touchConversation` + `maybeMergeMemory`，而 `maybeMergeMemory` 达到阈值（`SUMMARY_BATCH_SIZE=6` 条溢出）时会**同步再调一次 LLM 生成摘要**（秒级）→ 用户要等这次额外 LLM 调用完才看到答案第一个字；短回复时还会让 SSE 迟迟不 complete。
- `MemoryMergeService` 新增 `maybeMergeMemoryAsync(conversationId)`：`Schedulers.boundedElastic().schedule(...)` 异步执行，并用实例级 `Set<String> merging = ConcurrentHashMap.newKeySet()` 做**会话级去重**（同一会话已在合并则跳过本次，下一轮结束会再检查，不会漏）。原同步 `maybeMergeMemory` 保留不动。
- `ChatService` 统一「数据优先于记忆」：
  - `emitChunks(sink, full)` 瘦身为只推 token（去掉 conversationId/message 参数与记忆调用）。
  - 新增 `afterReply(conversationId, message)`：`touchConversation` 同步（毫秒级 DB update，保证会话列表排序即时正确）+ `maybeMergeMemoryAsync` 异步；异常只记日志。
  - `handlePlannerConversation` 返回值由 `String` 改为 `record PlannerOutcome(String reply, boolean needSaveExchange)`，**内部不再写记忆**——多步执行返回 `true`（需上层补写整对），回退 `answerDefault` 返回 `false`（记忆 Advisor 已自动落库，重复写会出现两遍）。
  - 5 处调用点顺序统一为「先出数据 → 再落库 → 再 afterReply」：planner（chat/stream）、clarify 追问（stream 里 token 先推、再 bindAgent+saveClarifyExchange）、常规单智能体（emitChunks 后才 unbindAgent）。同步 `chat()` 无法真正"先返回"，但异步 merge 让它响应也变快。
- 顺序约束（勿改）：`savePlannerExchange` 必须**同步**且在 `afterReply` 之前——摘要合并要能读到本轮消息；它只是 DB insert，毫秒级，不影响首字。
- 已知限制：`merging` 是实例级集合，多实例部署时不同实例可能重复合并（单机无影响）。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务**（纯后端改动，前端无需刷新）。

## 修复：天气追问「北京呢？」无法回答（11:46）
- 现象：多轮天气对话，"今天天气怎么样"→追问城市→"深圳"正常回答→"北京呢？"答不出。
- 根因：`unbindAgent()` 在每次正式回答后把会话上的智能体解绑；下一轮「北京呢？」进 `determineAgent` 时 `conv.agentId` 已空，走 `agentRouter.route("北京呢？")`。原 `AgentRouter` 路由**只拿孤立的当前消息、无历史上下文**，模型看到半句话「北京呢？」无法判断是天气追问，返回 `none()` → 落到通用助手；而通用助手不挂载工具（工具仅在命中/绑定智能体时才挂），于是查不了天气、表现为"无法回答"。
- 修复：给智能路由补「最近若干轮对话上下文」。
  - `AgentRouter.route` 增加三参重载 `route(message, pendingQuestion, recentContext)`；原两参/单参委托；System Prompt 增加第 4 条规则（短句明显承接上一轮时路由到同一智能体）+「对话上下文」块。
  - `ChatService`：新增 `recentContextText(conversationId)`（取 chatMemory 最近 6 条格式化）；`determineAgent` 未绑定分支与两处话题切换预检（chat/doStream）都传入该上下文（注意 `determineAgent` 只有 `conv`，用 `conv.getId()`）。
  - 参数抽取 `clarifyScopedHistory` 的"任务隔离"**保持不动**：「北京呢？」作为新天气任务，scoped 仅含该句，抽取器从「北京呢？」直接取 `city:北京`，不会与上一轮深圳串味。
- 效果：回答后解绑、下一轮靠上下文重新路由回天气智能体，连续追问「上海呢？」「广州呢？」均可正常应答；新话题（无对应智能体）仍正确走普通对话。
- `mvn -o compile` 通过（MVN_EXIT=0）。**需重启服务**。
